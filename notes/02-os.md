# 운영체제

## Process & Thread

### Q. process를 간단히 설명해 주세요.

> 핵심: process는 디스크에 있던 프로그램이 메모리에 올라가 CPU로 실제 실행되고 있는 상태입니다.
> 운영체제는 process마다 독립된 메모리 공간(code, data, heap, stack)을 줘서 서로 간섭하지 않게 합니다.

[[sim:process-memory]]

프로그램(program)은 디스크에 놓인 실행 파일, 즉 명령어 묶음일 뿐 아직 아무 일도 하지 않습니다. 이 파일을 더블클릭하거나 `./a.out`으로 실행하면 운영체제가 메모리에 자리를 만들고 파일 내용을 적재한 뒤 CPU 사용권을 줍니다. 이렇게 "실행 중인 프로그램"이 된 것이 process입니다. 같은 프로그램을 두 번 실행하면 program은 하나지만 process는 두 개가 생깁니다.

**메모리 관점**

CPU는 디스크가 아니라 메모리에 있는 명령어만 읽어 실행할 수 있습니다. 그래서 실행 전에 반드시 적재가 필요합니다. process가 받는 공간은 네 영역으로 나뉘고, process마다 따로 갖습니다.

| 영역 | 담기는 것 |
| --- | --- |
| Code | 실행할 기계어 명령어 (읽기 전용으로 두는 경우가 많음) |
| Data | 전역 변수, static 변수 (프로그램 시작부터 끝까지 유지) |
| Heap | `malloc`, `new`처럼 실행 중에 개발자가 요청하고 직접 반납하는 공간 |
| Stack | 함수 호출마다 쌓이는 지역 변수, 매개변수, 복귀 주소 (함수가 끝나면 사라짐) |

heap은 낮은 주소에서 높은 주소로, stack은 반대로 자라면서 중간의 빈 공간을 서로 나눠 씁니다.

**CPU 관점**

적재만으로는 실행이 아닙니다. CPU 안의 PC(Program Counter) register가 "다음에 실행할 명령어의 주소"를 들고 있고, CPU는 그 주소의 명령어를 읽어 실행한 뒤 PC를 다음 명령어로 옮기는 일을 반복합니다. 메모리에 올라가 있고 PC를 따라 명령어가 실행되고 있다는 두 가지를 함께 말하면 완성된 답변입니다.

#### Q. process의 memory영역(code, data, stack, heap)에 대해서 설명해 주세요.

code는 프로그램 명령어 자체가 놓이는 곳이고, data는 전역/static 변수처럼 수명이 프로그램 전체인 값이 놓입니다. heap은 실행 중 필요한 만큼 요청하고 직접 해제하는 동적 공간이며(해제를 잊으면 메모리 누수), stack은 함수 호출 단위로 지역 변수와 매개변수, 복귀 주소가 쌓였다가 함수가 끝나면 걷히는 공간입니다.

```c
int total = 0;              // data 영역
int add(int a, int b) {     // 매개변수 a, b: stack
    int sum = a + b;        // 지역 변수 sum: stack
    return sum;
}
int main() {
    int *buf = malloc(64);  // buf 변수는 stack, 가리키는 64바이트는 heap
    free(buf);              // heap은 직접 반납
}
```

### Q. ⭐⭐⭐⭐ Multi process에 대해서 설명해 주세요.

> 핵심: multi process는 여러 process가 동시에 실행되는 것으로, 코어 하나에서는 시간을 잘게 쪼개 번갈아 실행하는 시분할(동시성)로 구현됩니다.
> 번갈아 실행하려면 중단 시점의 상태(context)를 PCB에 저장하고 복구하는 context switch가 필요합니다.

[[sim:context-switch]]

"동시에"는 두 가지 뜻이 있습니다.

| | 동시성(concurrency) | 병렬성(parallelism) |
| --- | --- | --- |
| 환경 | 코어 1개 | 코어 여러 개 |
| 실제 모습 | 번갈아 실행해서 동시처럼 보임 | 정말로 같은 순간에 실행됨 |

병렬성은 뜻만 알면 충분하고, 면접에서 진짜 묻는 것은 코어 하나가 어떻게 여러 일을 하는 것처럼 보이게 하느냐, 즉 동시성의 원리입니다.

**시분할 시스템(time sharing)**

여러 process는 메모리와 CPU를 나눠 씁니다. 메모리는 각자 자기 영역을 차지한 채 동시에 올라가 있을 수 있지만, CPU 코어 하나는 한 순간에 한 process의 명령어만 처리합니다. 대신 운영체제가 수 ms 정도의 짧은 시간(time slice)마다 CPU를 다른 process에 넘기기 때문에, 사람 눈에는 음악 재생, 다운로드, 메신저가 한꺼번에 도는 것처럼 보입니다.

운영체제는 메모리 보호도 맡습니다. 각 process가 자기 영역만 접근하게 막아서, 한 process의 버그가 다른 process의 메모리를 망가뜨리지 못하게 합니다.

**PC register의 역할**

CPU는 PC가 가리키는 곳의 명령어를 실행합니다. process A를 돌릴 때는 PC가 A의 code 영역 안을 가리키고, B 차례가 되면 B의 code 영역 안을 가리킵니다. 즉 PC 값을 바꿔 끼우는 것이 곧 실행 대상을 바꾸는 것입니다.

**Context와 PCB**

차례를 뺏긴 process가 나중에 이어서 실행하려면 "어디까지 했고, register에 무슨 값이 있었는지"를 기억해야 합니다. 이렇게 process의 현재 실행 상태를 복원하는 데 필요한 정보 전체를 context라고 하고, 운영체제는 이를 process마다 PCB(Process Control Block)라는 자료구조에 보관합니다. PCB는 중요한 정보라서 사용자 코드가 건드릴 수 없는 커널 영역에 둡니다.

| PCB 항목 | 내용 |
| --- | --- |
| Process ID | process를 구분하는 번호 |
| State | 현재 상태 (new, ready, running, waiting, terminated 등) |
| PC | 다음에 실행할 명령어 주소 |
| Registers | 중단 시점의 CPU register 값 |
| 메모리 정보 | page table, 주소 범위 등 |
| 스케줄링 정보 | 우선순위 등 |

**Context switch**

CPU를 쓰던 process를 바꾸는 작업입니다. 순서는 다음과 같습니다.

1. 실행 중이던 A의 register, PC 값을 A의 PCB에 저장
2. 다음 차례인 B의 PCB에서 값을 읽어 register, PC에 복원
3. B가 자기 PC 위치부터 이어서 실행

전환하는 동안에는 사용자 작업이 진행되지 않으므로 순수한 오버헤드입니다. 너무 자주 전환하면 오히려 느려집니다.

**꼬리질문을 위한 정리**

- 시분할 -> context -> PCB -> context switch -> 메모리 영역 순서로 말하면 흐름이 매끄럽습니다.

#### Q. process의 context는 무엇인가요?

context는 process가 지금 어디까지 어떤 상태로 실행됐는지를 재현할 수 있게 하는 정보의 총합입니다. 대표적으로 PC 값, register 값, 메모리 매핑 정보가 있고, 운영체제는 이를 PCB에 저장해 두었다가 다시 CPU를 줄 때 복원합니다.

#### Q. PCB(Process Control Block)에 저장되는 것들은 무엇이 있나요?

PCB는 운영체제가 process 하나를 관리하려고 만든 자료구조입니다. 주요 항목은 다음과 같습니다.

- process ID
- process state
- PC 값
- 나머지 CPU register 값
- 스케줄링 정보(우선순위, 대기 큐 위치 등)
- 메모리 관리 정보(page table, 주소 범위 등)

#### Q. Context switch에 대해서 설명해 주세요.

CPU를 쓰던 process를 다른 process로 교체하는 동작입니다. 나가는 process의 PC와 register를 그 process의 PCB에 기록하고, 들어오는 process의 PCB에 있던 값을 CPU에 되돌려 놓으면 들어온 process는 자기가 멈췄던 지점부터 계속 실행합니다. 이 시간 동안 실제 작업은 하지 않으므로 전환 횟수가 많을수록 손해입니다.

#### Q. process의 state에는 어떤 것들이 있나요?

크게 세 가지로 나눠 설명하면 됩니다.

| 상태 | 의미 |
| --- | --- |
| running | 지금 CPU를 쥐고 명령어를 실행 중 |
| ready | 실행할 준비는 다 됐고 CPU 차례만 기다림 |
| blocked(waiting) | CPU를 줘도 할 일이 없는 상태. 디스크 읽기, 네트워크 응답 같은 I/O 완료를 기다림 |

여기에 생성 직후의 new, 종료 단계의 terminated를 더해 5-state로 설명하기도 합니다. 시간 할당이 끝나면 running -> ready, I/O를 요청하면 running -> blocked, I/O가 끝나면 blocked -> ready로 이동합니다.

### Q. ⭐⭐ Multi thread에 대해서 설명해 주세요.

> 핵심: thread는 process 안에서 실행 흐름을 나눈 단위로, code, data, heap은 같이 쓰고 stack과 PC는 각자 가집니다.
> multi thread는 한 process가 여러 작업을 동시에 처리하게 해 주는 구조입니다.

[[sim:process-memory]]

예를 들어 동영상 플레이어 하나(process) 안에서 영상 디코딩, 자막 표시, 네트워크 버퍼링을 각각 다른 thread가 맡을 수 있습니다. 세 작업은 같은 영상 데이터와 설정 값(공유 영역)을 보면서도 각자 진행 위치를 따로 가져야 합니다.

**무엇을 공유하고 무엇을 따로 갖나**

- 공유: code, data, heap (같은 process에 속하므로 같은 변수와 객체를 바로 접근)
- 독립: stack, PC register, 그 밖의 register 값

**왜 stack과 PC는 따로 필요한가**

thread마다 서로 다른 함수를 호출하고 그 안에서 실행이 진행됩니다. 함수 호출에는 매개변수 전달, 복귀 주소 저장, 지역 변수 보관이 필요하고 이는 stack에 쌓입니다. 두 thread가 stack 하나를 같이 쓰면 호출 기록이 뒤섞여 함수가 제대로 돌아갈 수 없습니다. PC도 마찬가지로, thread끼리 context switch가 일어났을 때 각자 이어서 실행할 코드 위치를 기억해야 하기 때문에 따로 둡니다.

#### Q. thread는 왜 독립적인 stack memory영역이 필요한가요?

thread의 존재 이유가 독립된 흐름으로 함수를 호출하는 것이기 때문입니다. 호출 중인 함수의 지역 변수, 인자, 복귀 주소가 stack에 쌓이는데, thread A와 B가 같은 stack을 쓰면 A가 쌓은 프레임 위에 B가 덮어써서 복귀 주소가 어긋납니다. 그래서 thread마다 별도의 stack을 할당합니다.

#### Q. process와 thread를 비교설명 해주세요.

process는 운영체제로부터 자원(메모리, 파일 등)을 받는 단위이고, thread는 그 자원을 가지고 실제로 CPU에서 실행되는 흐름의 단위입니다. process는 code, data, heap, stack을 모두 독립적으로 가지는 반면, 같은 process의 thread들은 stack만 따로 갖고 나머지 세 영역은 공유합니다. 모든 process는 최소 하나의 thread(main thread)를 가집니다.

### Q. ⭐⭐ multi process와 multi thread를 비교설명해 주세요.

> 핵심: multi thread는 가볍고 전환과 통신이 빠른 대신 동기화 문제와 장애 전파 위험이 있고, multi process는 무겁지만 격리되어 안정적입니다.
> 격리가 중요하면 process, 데이터 공유와 전환이 잦으면 thread를 고릅니다.

| | multi process | multi thread |
| --- | --- | --- |
| 메모리/자원 | 각자 독립 공간이라 많이 사용 | 대부분 공유해서 적게 사용 |
| 생성, 전환 비용 | 큼 | 작음 |
| 통신 | IPC 필요 (상대적으로 비쌈) | 공유 변수로 직접 접근 (싸다) |
| 안정성 | 한 process가 죽어도 다른 process는 무사 | 한 thread의 치명적 오류가 process 전체를 종료시킬 수 있음 |
| 주의점 | IPC 설계 | 동기화(race condition, deadlock) |

thread 전환이 빠른 이유는 같은 주소 공간을 쓰기 때문에 메모리 매핑을 바꿔 끼울 필요가 없고, CPU 캐시나 주소 변환 정보를 그대로 활용할 수 있기 때문입니다. process를 새로 만들려면 주소 공간과 자원을 새로 할당하는 system call 비용도 듭니다.

**실제 사례**

브라우저가 좋은 예입니다. 탭 하나가 멈춰도 다른 탭은 살아 있도록 탭마다 process를 분리하는 설계가 있고(격리 우선), 한 process 안에서 thread 여러 개로 렌더링과 네트워크를 나눠 처리하는 설계도 있습니다(자원 효율 우선).

#### Q. multi thread가 multi process보다 좋은 점은 무엇인가요?

메모리와 시스템 자원 사용이 적습니다. thread를 만들 때는 새 주소 공간을 할당하는 과정이 없어 생성이 빠르고, 전환할 때도 주소 공간이 그대로라 캐시 내용을 버리지 않아도 됩니다. 또 thread끼리는 힙의 객체나 전역 변수를 곧바로 읽고 쓰면 되므로 IPC를 거치는 process 간 통신보다 데이터 교환 오버헤드가 훨씬 작습니다.

#### Q. multi thread가 multi process보다 안좋은 점은 무엇인가요?

공유 자원을 동시에 건드리면 race condition이 생기므로 lock 등 동기화 설계가 필수이고, 디버깅이 어렵습니다. 또 같은 주소 공간을 쓰기 때문에 한 thread가 잘못된 메모리 접근으로 비정상 종료하면 process 전체가 함께 죽을 수 있습니다.

### Q. ⭐⭐ multi process환경에서 process간에 데이터를 어떻게 주고 받을까요?

> 핵심: process는 주소 공간이 격리되어 있어서 IPC(Inter-Process Communication)라는 운영체제 제공 통로를 써야 합니다.
> IPC는 크게 shared memory와 message passing 두 모델로 나뉩니다.

[[sim:ipc]]

한 process가 다른 process의 변수를 주소로 직접 읽을 수 없습니다. 보호를 위해 일부러 막아 놓은 것이므로, 데이터를 주고받으려면 운영체제가 중개하거나 허용한 경로를 거쳐야 합니다.

**공유 메모리(shared memory)**

커널에 요청해서 여러 process가 함께 매핑하는 메모리 구간을 하나 만듭니다. 설정이 끝난 뒤에는 그 구간을 일반 변수처럼 읽고 쓰면 되고, 커널이 매번 끼어들지 않으므로 빠릅니다. 대신 두 process가 동시에 같은 위치에 쓰면 값이 꼬이므로 동기화(semaphore 등)를 process들이 직접 책임져야 합니다. POSIX의 `shm_open`과 `mmap` 조합이 대표 API입니다.

**메시지 전달(message passing)**

`send`와 `receive`라는 system call로 커널을 거쳐 메시지를 전달합니다. 커널이 순서와 전달을 관리해 주므로 안전하고 구현하기 쉽지만, 호출마다 커널을 통과해 공유 메모리보다 느립니다. 충돌을 신경 쓸 필요가 적어 소량 데이터에 적합합니다. 대표 예로 pipe, socket, message queue가 있습니다.

| | 공유 메모리 | 메시지 전달 |
| --- | --- | --- |
| 속도 | 빠름 (설정 후 커널 개입 없음) | 상대적으로 느림 (매번 system call) |
| 동기화 | 직접 구현해야 함 | 커널이 어느 정도 제공 |
| 적합한 경우 | 대용량, 빈번한 교환 | 소량, 단순한 교환 |

#### Q. IPC의 예시를 들어주실 수 있나요?

공유 메모리 계열은 POSIX 공유 메모리, `mmap`으로 파일이나 익명 영역을 공유하는 방식이 있고, 메시지 전달 계열은 pipe(예: 셸의 `ls | grep txt`), 같은 기기나 네트워크 너머 통신이 가능한 socket, 커널이 관리하는 message queue 등이 있습니다.

#### Q. 공유메모리와 메시지 전달 모델의 장단점을 설명해 주세요.

공유 메모리는 처음 한 번 영역을 잡을 때만 커널이 관여하고 이후에는 메모리 접근 속도로 통신하므로 빠르지만, 동시 접근에 의한 충돌을 직접 막아야 하는 부담이 있습니다. 메시지 전달은 커널이 전달과 순서를 맡아 단순하고 안전하지만, 데이터를 커널 버퍼를 거쳐 복사하고 system call을 반복하므로 느립니다.

### Q. ⭐ Multi process/thread 환경에서 동기화 문제를 어떻게 해결하나요?

> 핵심: 공유 자원에 동시에 접근하면 실행 순서에 따라 결과가 달라지는 race condition이 생기므로, 임계 구역을 lock으로 보호합니다.
> 한 번에 하나만 들어가게 하면 mutex, 정해진 개수까지 허용하면 semaphore입니다.

**동기화 문제는 왜 생기는가**

`likes++` 한 줄은 CPU 눈에는 한 동작이 아닙니다.

1. 메모리에서 `likes` 값을 register로 읽는다 (load)
2. register 값을 1 증가시킨다
3. 결과를 메모리의 `likes`에 되쓴다 (store)

`likes`가 10일 때 thread A와 B가 각각 `likes++`를 한 번씩 한다고 합시다. A가 값 10을 읽은 직후 context switch로 B가 실행되어 10을 읽고 11을 저장하고, 다시 A로 돌아가 자기 register의 10에서 계산한 11을 저장하면, 12여야 할 값이 11이 됩니다. 이렇게 둘 이상이 같은 자원을 동시에 조작하고 결과가 접근 순서에 좌우되는 상황이 경쟁 상태(race condition)입니다.

[[sim:race-condition]]

**임계 구역(critical section)**

공유 자원을 건드리는 코드 구간입니다. 이 구간은 한 번에 하나의 process/thread만 실행하도록 보장해야 하고, 그 효과를 원자적(atomic)이라고 표현합니다. 코드 구조는 보통 아래와 같습니다.

```text
entry section      // 들어가도 되는지 허락받음 (lock 획득)
  critical section // 공유 자원 접근
exit section       // 나왔음을 알림 (lock 반환)
remainder section  // 나머지 코드
```

**Mutex**

mutual exclusion의 줄임말로, 임계 구역에 들어갈 수 있는 주체를 1개로 제한하는 lock입니다.

```text
acquire()    // lock이 잠겨 있으면 풀릴 때까지 기다림
  likes++    // critical section
release()    // lock을 풀어 다음 대기자에게 기회를 줌
```

[[sim:mutex]]

lock을 잡은 쪽이 풀어야 합니다(소유권 개념). lock을 기다리는 방식 중 반복문으로 계속 확인하는 busy waiting(spinlock)은 기다리는 동안 CPU를 낭비하는 단점이 있어서, 오래 기다릴 가능성이 있으면 대기 큐에 재우고 깨워 주는 방식을 씁니다.

**Semaphore**

정수 S로 사용 가능한 자원의 개수를 나타냅니다.

```text
wait(S)      // S가 0이면 대기, 아니면 S를 1 감소시키고 진입
  ...        // critical section
signal(S)    // S를 1 증가시켜 대기자 하나를 깨움
```

예를 들어 DB 커넥션 풀에 연결이 3개 있다면 S를 3으로 시작합니다. 네 번째 요청은 S가 0이므로 누군가 반납(signal)할 때까지 기다립니다. S가 0과 1만 가지면 binary semaphore라 하고, 사실상 mutex처럼 동작합니다.

[[sim:semaphore]]

#### Q. mutex와 semaphore 기법을 비교 설명해 주세요.

mutex는 동시에 1개만 임계 구역에 들어갈 수 있는 잠금이고 lock을 건 주체가 직접 푸는 것이 원칙입니다. semaphore는 카운터 값만큼의 주체가 동시에 자원을 쓸 수 있게 하는 신호 장치이며 다른 주체가 signal을 보내도 됩니다. 그래서 binary semaphore는 mutex와 비슷하게 쓰이지만 소유권이 없다는 점에서 개념이 완전히 같지는 않습니다.

### Q. 교착상태(Deadlock)에 대해서 간단히 설명해 주세요.

> 핵심: deadlock은 둘 이상의 thread가 서로 상대가 쥔 자원을 기다리며 영원히 멈추는 상태입니다.
> 상호 배제, 점유 대기, 비선점, 순환 대기 네 조건이 모두 성립할 때 발생할 수 있고, 하나라도 깨면 막을 수 있습니다.

[[sim:deadlock]]

가장 흔한 형태는 lock 순서가 엇갈리는 경우입니다.

```text
Thread 1: lock(A) -> lock(B)
Thread 2: lock(B) -> lock(A)
```

1이 A를, 2가 B를 잡은 상태에서 서로 상대 것을 요청하면 둘 다 영원히 기다립니다.

**발생 조건 4가지 (동시에 모두 성립해야 함)**

1. 상호 배제(mutual exclusion): 자원을 한 번에 한 주체만 쓸 수 있다.
2. 점유 대기(hold-and-wait): 자원을 쥔 채로 다른 자원을 더 기다린다.
3. 비선점(no preemption): 쥔 자원을 남이 강제로 뺏을 수 없고 주인이 내놓아야 한다.
4. 순환 대기(circular wait): 기다리는 관계가 원 모양으로 이어진다. (1이 2를, 2가 3을, 3이 1을 기다림)

**해결 방법 4가지**

| 방법 | 내용 | 특징 |
| --- | --- | --- |
| 무시 | 발생해도 따로 대처하지 않음 (재부팅 등으로 해결) | 오버헤드가 없고 드물게 발생하는 시스템에서 현실적으로 많이 선택 |
| 예방 | 네 조건 중 하나를 구조적으로 불가능하게 만듦 | 가장 현실적인 것은 자원에 번호를 매겨 항상 번호 순으로만 요청해 순환 대기를 차단. 자원 활용도 저하 |
| 회피 | 요청 시점에 안전한 상태인지 계산해 위험하면 대기시킴 (은행원 알고리즘) | 앞으로의 최대 요구량 정보가 필요 |
| 탐지와 회복 | 일단 허용하고 주기적으로 교착을 탐지, 프로세스 종료나 자원 회수로 복구 | 탐지와 복구 비용이 듦 |

위 예시는 두 thread가 항상 A를 먼저, B를 나중에 잡도록 순서를 통일하면 순환 대기가 사라져 해결됩니다.

#### Q. deadlock은 언제 발생하게 되나요?

상호 배제, 점유 대기, 비선점, 순환 대기 네 조건이 동시에 만족될 때 발생할 수 있습니다. 자원을 독점해서 쓰고, 쥔 채로 다른 자원을 더 기다리며, 남이 뺏을 수 없고, 기다림이 꼬리를 물어 원을 이루는 상황입니다. 네 조건 중 하나라도 성립하지 않으면 deadlock은 생기지 않습니다.

## Memory

### Q. paging 이란 뭔가요?

> 핵심: paging은 process의 주소 공간을 같은 크기의 page로 쪼개 물리 메모리의 비연속적인 frame에 나눠 담는 기법입니다.
> 논리 주소를 물리 주소로 바꾸는 일은 process별 page table이 담당합니다.

[[sim:paging]]

**용어**

- 논리 주소(logical address): process가 보는 가상의 주소. process마다 0번지부터 시작하는 자기만의 공간입니다.
- 물리 주소(physical address): RAM 위의 실제 위치.
- 주소 바인딩(address binding): 논리 주소를 물리 주소에 대응시키는 과정.

**동작**

물리 메모리를 page와 같은 크기의 frame으로 미리 잘라 두고, process의 논리 공간도 page 단위로 자릅니다. page는 빈 frame 아무 곳에나 넣을 수 있고, 어느 page가 어느 frame에 있는지를 기록한 표가 page table입니다. 논리 주소는 (page 번호, offset)으로 해석합니다.

예시: page 크기가 1KB(1024바이트)이고 page table이 `page 2 -> frame 9`일 때, 논리 주소 2500은 page 2(2048부터 시작), offset 452입니다. 물리 주소는 `9 * 1024 + 452 = 9668`입니다.

page가 흩어져 있어도 process 입장에서는 연속된 공간처럼 보이고, 빈 frame만 있으면 어디든 쓸 수 있어 메모리를 유연하게 활용합니다.

#### Q. paging 기법 사용시 발생할 수 있는 메모리 단편화(Memory fragmentation) 문제에 대해 설명하시오

단편화는 빈 메모리 총량은 충분한데 조각나서 쓰지 못하는 현상입니다. 외부 단편화(할당 단위 사이사이에 생기는 못 쓰는 틈)와 내부 단편화(할당받은 공간 안에서 남는 낭비)로 나뉩니다. paging은 크기가 같은 frame 어디에든 넣을 수 있어 외부 단편화가 없습니다. 다만 process 크기가 page 크기의 정확한 배수가 아니면 마지막 page는 일부만 채워지고 나머지가 낭비되어 내부 단편화가 생깁니다. 예를 들어 4KB page에 9KB process는 3개 page(12KB)를 받아 3KB가 남습니다.

### Q. segmentation에 대해서 설명해 주세요.

> 핵심: segmentation은 주소 공간을 code, data, stack처럼 의미(기능) 단위의 segment로 나눠 물리 메모리에 흩어 배치하는 기법입니다.
> segment 크기가 제각각이라 주소가 (segment 번호, offset)이고, segment table의 base와 limit으로 변환합니다.

[[sim:segmentation]]

paging이 기계적으로 같은 크기로 자르는 방식이라면, segmentation은 프로그램의 논리 구조대로 자릅니다. 그래서 code는 읽기 전용, stack은 읽기/쓰기처럼 segment 단위로 접근 권한을 걸거나 다른 process와 공유하기 좋습니다.

**주소 변환**

segment table의 각 항목은 base(물리 메모리상 시작 주소)와 limit(길이)을 가집니다. 논리 주소 (s, d)는 다음과 같이 처리합니다.

1. `d < limit[s]`인지 확인한다.
2. 통과하면 물리 주소는 `base[s] + d`.
3. 범위를 벗어나면 접근 위반으로 trap이 걸리고 보통 process는 segmentation fault로 종료된다.

예시: segment 1의 base가 8000, limit이 600이라면 (1, 200)은 8200으로 변환되고, (1, 700)은 600을 넘으므로 오류입니다.

#### Q. segmentation의 메모리 단편화(Memory fragmentation) 문제에 대해 설명해 주세요.

segment를 필요한 크기 그대로 할당하므로 내부 단편화는 거의 없습니다. 하지만 크기가 다른 segment가 계속 올라갔다 내려가면 사이사이 작은 빈 구멍이 남아 외부 단편화가 생깁니다. 총 빈 공간이 충분해도 연속된 큰 구멍이 없어서 새 segment를 못 넣는 일이 생기며, 해결하려면 compaction(메모리 조각 모으기) 같은 비용이 큰 작업이 필요합니다.

#### Q. paging과 segmentation의 차이는 뭔가요?

paging은 고정 크기로 나누고(내부 단편화 발생, 외부 단편화 없음), 사용자가 보는 의미와 무관한 물리적 구분입니다. segmentation은 기능 단위로 가변 크기로 나누고(외부 단편화 발생, 내부 단편화 없음), 보호와 공유를 의미 단위로 하기 쉽습니다. 주소 표현도 paging은 (page 번호, offset), segmentation은 (segment 번호, offset)이지만 후자는 limit 검사가 추가됩니다.

#### Q. paged segmentation 기법에 대해 설명하시오

segmentation으로 먼저 의미 단위로 나눈 다음, 각 segment를 다시 고정 크기 page로 쪼개 frame에 배치하는 혼합 방식입니다. segment 단위의 보호와 공유라는 segmentation의 장점을 유지하면서, 실제 배치는 paging으로 하므로 외부 단편화 문제가 사라집니다. 대가로 segment table과 page table을 모두 거치는 주소 변환 구조가 복잡해집니다.

### Q. ⭐ 가상 메모리에 대해서 설명해 주세요.

> 핵심: 가상 메모리는 process 전체가 물리 메모리에 올라오지 않아도 실행되도록, 필요한 page만 올리고 나머지는 디스크(swap)에 두는 기법입니다.
> 덕분에 프로그램이 물리 메모리보다 커도 돌아가고, 개발자는 메모리 크기를 신경 쓰지 않고 짤 수 있습니다.

[[sim:virtual-memory]]

가상 메모리는 개발자가 보는 논리 메모리와 실제 RAM을 분리하는 개념입니다. 프로그램은 넉넉한 연속 주소 공간이 있다고 가정하고 동작하고, 운영체제와 MMU가 그중 지금 필요한 부분만 RAM에 두고 나머지는 디스크의 swap 영역에 보관합니다. 프로그램은 실행 중에 코드의 일부분만 집중적으로 쓰는 경향(지역성)이 있어 이 방식이 잘 통합니다.

**요구 페이징(demand paging)**

page를 미리 다 올리지 않고 CPU가 처음 접근하려 할 때 올리는 방식입니다. 실제 필요한 page만 올라가므로 메모리 사용량과 초기 적재 I/O가 줄어듭니다. page table에는 유효/무효 비트(valid/invalid bit)를 두어 해당 page가 메모리에 있는지(유효), 없는지(무효)를 표시합니다.

**Page fault**

CPU가 무효 비트인 page에 접근할 때 발생하는 사건입니다. 처리 순서는 다음과 같습니다.

1. CPU가 어떤 page를 참조한다.
2. MMU가 page table을 보고 무효임을 확인해 page fault trap(예외)을 발생시킨다.
3. 운영체제가 그 page의 디스크 위치를 찾아 빈 frame에 읽어 온다.
4. page table을 갱신하고(무효 -> 유효) 중단된 명령어를 다시 실행한다.

디스크 읽기는 메모리 접근보다 수만 배 느려서 page fault가 잦으면 성능이 급격히 떨어집니다(thrashing).

**Page 교체 알고리즘**

빈 frame이 없을 때는 이미 올라와 있는 page 하나를 내보내야 하고, 누구를 내보낼지 정하는 규칙이 교체 알고리즘입니다. 목표는 page fault 횟수를 줄이는 것, 즉 앞으로 가장 쓰이지 않을 page를 내보내는 것입니다.

| 알고리즘 | 기준 | 특징 |
| --- | --- | --- |
| FIFO | 가장 먼저 들어온 page | 구현 쉬움, 자주 쓰는 page도 오래됐다고 쫓겨날 수 있음 |
| OPT(최적) | 앞으로 가장 오래 안 쓰일 page | fault가 최소지만 미래를 알아야 해서 구현 불가, 비교 기준으로만 사용 |
| LRU | 가장 오랫동안 참조되지 않은 page | 과거 사용 기록으로 미래를 추정, 성능 좋아 널리 쓰임 |
| LFU | 참조 횟수가 가장 적은 page | 과거에 많이 쓰고 지금은 안 쓰는 page가 남는 문제, 카운터 비용 |

프레임 3개에 참조 순서가 `1 2 3 1 4 1 2`일 때 FIFO는 6번, LRU는 5번 fault가 납니다. LRU는 최근에 쓴 1을 지키고 2를 내보내기 때문입니다.

#### Q. 요구페이징(demand paging)이란 무엇인가요?

CPU가 실제로 접근하는 시점에 그 page를 메모리에 올리는 방식입니다. 실행에 필요한 부분만 올라오므로 메모리를 아끼고 프로그램 시작 시 전체를 읽어 들이는 I/O 부담이 줄지만, 처음 접근하는 page마다 page fault를 한 번씩 겪습니다.

#### Q. 페이지 교체 알고리즘(replacement algorithm)을 아는대로 말씀해주세요.

FIFO, OPT(최적 교체), LRU, LFU가 있고, 현실에서는 LRU를 근사한 방식(clock 알고리즘 등)이 많이 쓰입니다.

#### Q. LRU알고리즘과 LFU 알고리즘을 비교 설명해 주세요.

LRU는 얼마나 오래전에 마지막으로 쓰였는지(최근성)를 기준으로 가장 오래 방치된 page를 내보냅니다. LFU는 지금까지 몇 번 쓰였는지(빈도)를 기준으로 가장 적게 쓰인 page를 내보냅니다. LRU는 최근 사용 패턴을 잘 따라가고, LFU는 한때 많이 쓰이고 지금은 안 쓰는 page가 남아 있는 약점과 횟수를 세는 비용이 있어서 상대적으로 덜 쓰입니다.
