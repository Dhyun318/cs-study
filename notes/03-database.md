# 데이터베이스

## DB 구조 & 설계

### Q. Primary key가 무엇인지 설명해 주세요.

> 핵심: 기본키(PK)는 후보키 중 대표로 뽑은 키로, 테이블의 모든 행을 하나씩 구분해 준다.
> NULL과 중복을 허용하지 않고, 테이블당 하나만 지정한다.

키 용어는 서로 포함 관계라서 한 줄씩 정리해 두면 꼬리질문에 바로 답할 수 있다.

**용어 정리**

**relation**은 DB에서 쓰는 형태를 갖춘 테이블이다. 조건은 두 가지이다.

1. 한 칸(cell)에는 값이 하나만 들어간다.
2. 완전히 똑같은 행이 두 개 있으면 안 된다.

실무에서는 table과 relation을 거의 같은 뜻으로 쓴다.

- 열: **column**(attribute)
- 행: **row**(tuple, record)

[[sim:db-keys]]

**키 종류**

예시로 `employee(emp_no, email, name, dept)` 테이블을 생각한다. 사번과 이메일은 사람마다 다르고, 이름과 부서는 겹칠 수 있다고 가정한다.

| 종류 | 정의 | 예시 |
|---|---|---|
| 슈퍼키 | 행을 유일하게 식별하는 속성 집합 (유일성만 만족) | (emp_no), (emp_no, name), (email, dept) |
| 후보키 | 슈퍼키 중 속성을 하나라도 빼면 유일성이 깨지는 것 (최소성까지 만족) | (emp_no), (email) |
| 기본키 | 후보키 중 대표로 고른 하나 (NULL 불가, 중복 불가, 테이블당 1개) | (emp_no) |
| 대체키 | 기본키가 되지 못하고 남은 후보키 | (email) |

기본키는 보통 변하지 않고 짧은 값을 고른다. 이메일처럼 바뀔 수 있는 값은 후보키여도 기본키로는 덜 적합하다.

#### Q. Primary Key와 Foreign Key에 대해 설명해 주세요.

> 핵심: PK는 자기 테이블의 행을 식별하는 키이고, FK는 다른 테이블의 PK를 가리켜 두 테이블을 잇는 컬럼이다.

**PK**는 후보키 중 하나라서 유일성과 최소성을 만족하고 NULL을 가질 수 없다.

**FK**는 다른 테이블(또는 자기 자신)의 PK를 참조하는 컬럼이며, **참조 무결성**을 지켜 준다. 즉 FK 값은 참조 대상 PK에 실제로 존재하는 값이어야 한다.

FK 컬럼은 중복되어도 되고, 정책에 따라 NULL도 허용된다.

#### Q. Candidate key에 대해 설명하시오.

> 핵심: 후보키는 유일성과 최소성을 모두 만족하는 컬럼(들)로, 기본키가 될 자격이 있는 키이다.

- **유일성**: 값으로 행을 하나만 찾을 수 있다.
- **최소성**: 속성을 하나라도 빼면 유일성이 깨진다.

후보키는 한 테이블에 여러 개 있을 수 있고, 그중 하나가 기본키로 선택된다.

#### Q. alternate key에 대해 설명하시오.

> 핵심: 대체키는 후보키 중 기본키로 선택되지 않고 남은 키이다. 보조키라고도 부른다.

위 예시에서 emp_no를 기본키로 골랐다면 email이 **대체키**이다.

대체키 컬럼에는 보통 **UNIQUE 제약**을 걸어 유일성을 보장한다.

#### Q. composite key에 대해 설명하시오.

> 핵심: 복합키는 컬럼 두 개 이상을 묶어야 비로소 행을 식별할 수 있는 후보키이다.

예를 들어 `order_item(order_id, product_id, qty)`를 보자.

- order_id만으로는 한 주문에 여러 상품이 있어 중복된다.
- product_id만으로도 여러 주문에 같은 상품이 있어 중복된다.

둘을 함께 묶으면 한 행으로 정해지므로 (order_id, product_id)가 **복합키**이다. 아래 N:M 관계의 연결 테이블에서 자주 등장한다.

### Q. 관계형 데이터베이스의 N:M 관계에 대해서 설명해 주세요.

> 핵심: N:M은 양쪽 엔티티가 서로 여러 개와 연결되는 관계이다.
> 테이블 두 개로는 직접 표현하지 못해서, 가운데에 연결(매핑) 테이블을 두고 두 개의 1:N으로 풀어낸다.

관계의 개수 비율을 **매핑 카디널리티**라고 하며 1:1, 1:N, N:M이 있다.

**1:N**

한 쪽의 행 하나가 상대 테이블의 여러 행과 연결되는 구조이다. 구현은 N쪽 테이블에 1쪽의 PK를 **FK**로 두는 방식이다.

예를 들어 작가 한 명은 책을 여러 권 쓸 수 있지만, 책 한 권의 대표 작가는 한 명이라고 하면 1:N이다.

```sql
author(author_id PK, name)
book(
  book_id PK,
  title,
  author_id FK
    -> author.author_id
)
```

작가의 소개글을 고쳐도 book 테이블은 건드릴 필요가 없다. 같은 정보를 여러 곳에 중복 저장하지 않아서 수정이 한 곳에서 끝난다.

**N:M**

한 쪽의 행이 상대의 여러 행과 연결되고, 상대도 마찬가지인 구조이다. 예를 들어 회원과 동호회는 회원 한 명이 여러 동호회에 가입하고, 동호회 하나에도 여러 회원이 있으니 N:M이다.

어느 한 쪽에 FK를 넣으면 컬럼 하나에 여러 값을 넣어야 해서 **정규형이 깨진다**. 그래서 연결 테이블을 만든다.

```sql
member(member_id PK, name)
club(club_id PK, title)
membership(
  member_id FK,
  club_id FK,
  joined_at,
  PRIMARY KEY
    (member_id, club_id)
)
```

membership의 한 행은 어느 회원이 어느 동호회에 가입했는지를 나타내고, (member_id, club_id)가 **복합 기본키**가 된다. 가입일 같은 관계 자체의 속성도 이 테이블에 둘 수 있다.

[[sim:er-relationship]]

#### Q. 1:N 관계에 대해서 설명해 주세요.

> 핵심: 1:N은 한 엔티티의 행 하나가 다른 엔티티의 여러 행과 연결되는 가장 흔한 관계이다.

N쪽 테이블이 1쪽의 PK를 FK로 들고 있는 형태로 구현한다.

대표적인 예는 다음과 같다.

- 부서와 직원
- 고객과 주문
- 게시글과 댓글

### Q. left outer join, inner join 차이를 설명해 주세요.

> 핵심: JOIN은 여러 테이블을 연결 조건으로 이어 하나의 결과로 만드는 연산이다.
> inner join은 양쪽에 모두 짝이 있는 행만, left outer join은 왼쪽 테이블의 모든 행을 남기고 짝이 없으면 오른쪽 값을 NULL로 채운다.

**예시 테이블**

`author`

| author_id | name |
|---|---|
| 1 | 한지우 |
| 2 | 오세린 |
| 3 | 문도윤 |

`book`

| book_id | title | author_id |
|---|---|---|
| 10 | 파이썬 입문 | 1 |
| 11 | 알고리즘 노트 | 1 |
| 12 | 시스템 설계 | 2 |
| 13 | 작자 미상 필사본 | NULL |

**inner join**

```sql
-- 양쪽에 짝이 있는 행만
SELECT b.title, a.name
FROM book b
INNER JOIN author a
  ON b.author_id = a.author_id;
```

결과는 세 행이다.

- 파이썬 입문 (한지우)
- 알고리즘 노트 (한지우)
- 시스템 설계 (오세린)

작가가 없는 필사본과 책이 없는 문도윤은 빠진다.

**left outer join**

```sql
-- 왼쪽(author)은 전부 유지
SELECT a.name, b.title
FROM author a
LEFT JOIN book b
  ON a.author_id = b.author_id;
```

결과에는 위 세 행에 더해, 책이 없는 문도윤이 title이 **NULL**인 행으로 나타난다. 필사본은 오른쪽(book) 쪽이라 왼쪽에 짝이 없으면 나오지 않는다.

**쓸 때 주의점**

- 어느 테이블을 왼쪽에 쓰느냐에 따라 결과가 달라진다. 기준이 되는 쪽을 **FROM**에 두면 헷갈리지 않는다.
- 짝이 없는 행만 찾고 싶다면 LEFT JOIN 후 `WHERE b.book_id IS NULL`을 붙인다.

### Q. ⭐ RDB - NoSQL를 비교 설명해 주세요.

> 핵심: RDB는 미리 정한 스키마의 테이블에 정규화해서 저장하고 트랜잭션에 강하다.
> NoSQL은 문서, 키-값 같은 유연한 모델로 저장하고 수평 확장에 유리하지만, 중복 저장이 생기기 쉬워 수정이 많은 데이터에는 불리하다.

**RDB (관계형)**

데이터를 테이블에 담고 **스키마**를 먼저 엄격하게 정의한다.

- 장점: 정규화로 같은 정보를 한 번만 저장하므로 무결성이 좋고, 값을 고칠 때도 한 곳만 바꾸면 된다.
- 단점: 데이터가 커지면 JOIN이 많은 복잡한 쿼리가 필요해지고, 구조를 바꾸기도 쉽지 않다.

대표 제품은 MySQL, PostgreSQL, Oracle이다.

**NoSQL**

SQL과 테이블 중심 모델을 따르지 않는 DB를 통칭한다. 대용량 데이터와 빠르게 바뀌는 요구사항에 대응하려고 나왔다.

모델에 따라 나뉜다.

- 문서: MongoDB
- 키-값: Redis, DynamoDB
- 컬럼 패밀리: Cassandra
- 그래프: Neo4j

문서 DB는 한 문서 안에 관련 데이터를 통째로 넣는 경우가 많아 조회가 단순하고 빠르다. 하지만 같은 정보가 여러 문서에 복제되면 수정 때 **전부 찾아 고쳐야** 한다.

```javascript
// MongoDB 예시
// 필드 구성이 문서마다 달라도 된다
db.createCollection("product")
db.product.insertOne({
  sku: "P-100",
  name: "텀블러",
  tags: ["주방", "보온"]
})
db.product.insertOne({
  sku: "P-200",
  name: "노트",
  stock: 40
})

// 전체 조회
db.product.find()
// 조건에 맞는 하나
db.product.findOne({ sku: "P-100" })
// 조건에 맞는 문서 삭제
db.product.deleteMany({ name: "노트" })
// 컬렉션 전체 삭제
db.product.drop()
```

**비교표**

| 항목 | RDB | NoSQL |
|---|---|---|
| 저장 모델 | 테이블 | 문서, 키-값, 그래프 등 |
| 스키마 | 엄격, 사전 정의 | 유연, 필드 추가 자유 |
| 강점 | 무결성, 중복 최소화, 수정 유리, 강한 트랜잭션 | 구조 변경 용이, 수평 확장 용이 |
| 약점 | JOIN 증가, 수평 확장 어려움 | 중복 저장, 수정 시 여러 곳 반영, 구조 보장 약함 |
| 어울리는 경우 | 구조 명확, 수정 잦음 (결제, 재고) | 구조 유동적, 조회 위주, 초대용량 |

**Scale-up vs Scale-out**

- **Scale-up**(수직 확장): 서버 한 대의 CPU, 메모리, 디스크를 키운다.
- **Scale-out**(수평 확장): 서버 대수를 늘려 데이터를 나눈다.

수직 확장은 단순하지만 비용이 급격히 올라가고 한계가 있다.

RDB도 **샤딩**으로 수평 확장할 수 있다. 하지만 데이터가 여러 서버로 갈라지면 JOIN과 분산 트랜잭션이 매우 복잡해지고 ACID를 유지하기 까다롭다.

NoSQL은 처음부터 분산을 염두에 두고 JOIN과 강한 트랜잭션을 줄이는 대신 확장성을 얻은 경우가 많다. 다만 최근에는 NoSQL도 제한된 트랜잭션을 지원하고, RDB도 확장 기능을 갖추어 경계가 흐려지는 추세이다.

#### Q. Nosql은 언제 사용하면 좋을까요?

> 핵심: 데이터 구조가 자주 바뀌거나 아직 불확실할 때, 조회 위주일 때, 데이터가 매우 커서 scale-out이 필요할 때 적합하다.

예를 들어 다음과 같은 경우이다.

- 로그
- 사용자 활동 기록
- 캐시
- 상품마다 속성이 다른 카탈로그

중복 저장된 값을 고칠 일이 적어야 부담이 작다.

#### Q. RDB는 언제 사용하면 좋을까요?

> 핵심: 구조가 명확하고 잘 바뀌지 않으며, 수정이 잦고 정합성이 중요한 시스템에 적합하다.

결제, 재고, 회원 정보처럼 값이 틀리면 안 되는 데이터가 대표적이다.

정규화 덕분에 한 곳만 고치면 되고 트랜잭션도 강하게 보장된다.

## Transaction

### Q. ⭐⭐ Transaction을 간단히 설명해 주세요.

> 핵심: 트랜잭션은 하나의 논리적 작업을 이루는 쿼리들의 묶음으로, DB 상태를 바꾸는 최소 작업 단위이다.
> 전부 성공하거나 전부 취소되어야 하고, 이를 ACID(원자성, 일관성, 고립성, 지속성)로 보장한다.

**예시: 콘서트 좌석 예매**

좌석을 확정하는 쿼리와 결제 내역을 남기는 쿼리가 있다. 좌석만 확정되고 결제 기록이 사라지면 데이터가 어긋난다.

두 쿼리는 쪼갤 수 없는 한 작업이라서, 둘 다 반영되거나 둘 다 없던 일이 되어야 한다. 이 묶음이 **트랜잭션**이다.

**필요한 이유**

- 장애가 나도 어디까지 반영됐는지 기준 단위가 있어 복구할 수 있다.
- 여러 작업이 같은 데이터를 동시에 만져도 서로 간섭하지 않도록 분리할 수 있다.

```sql
START TRANSACTION;

UPDATE seat
  SET status = 'SOLD',
      owner_id = 7
  WHERE seat_id = 'A-12';
INSERT INTO payment
  (user_id, seat_id, amount)
  VALUES (7, 'A-12', 55000);

-- 둘 다 확정 (문제가 생기면 ROLLBACK)
COMMIT;
```

**ACID**

- **Atomicity(원자성)**
  - 작업이 전부 수행되거나 전혀 수행되지 않는다(all or nothing).
  - 중간에 실패하면 시작 전 상태로 되돌린다.
- **Consistency(일관성)**
  - 트랜잭션이 끝나면 DB가 정의된 규칙(제약조건, 타입, 참조 관계 등)을 만족해야 한다.
  - 예를 들어 재고가 음수가 되면 안 된다는 규칙이 있다면, 이를 어기는 트랜잭션은 성공할 수 없다.
- **Isolation(고립성)**
  - 동시에 실행되는 트랜잭션들이 서로의 중간 결과를 보거나 방해하지 못하게 한다.
  - 이를 위한 DBMS의 기능이 동시성 제어(concurrency control)이다.
- **Durability(지속성)**
  - 커밋된 결과는 이후 정전이나 장애가 나도 사라지지 않는다.
  - 보통 로그를 디스크에 먼저 기록하는 방식(**WAL**)으로 보장한다.

**동시성 제어와 갱신 손실**

두 트랜잭션이 같은 값을 읽고 각자 고친 뒤 쓰면, 나중에 쓴 쪽이 먼저 쓴 쪽의 결과를 덮어써서 한 번의 갱신이 사라질 수 있다. 이를 **갱신 손실**(lost update)이라고 한다.

예를 들어 재고가 10개일 때 두 주문이 동시에 10을 읽고 각각 9로 쓰면, 2개가 팔렸는데 재고는 1개만 줄어든다.

가장 기본적인 해결책은 **Lock**이다. 데이터를 수정 중인 트랜잭션이 그 데이터에 잠금을 걸면 다른 트랜잭션은 잠금이 풀릴 때까지 기다린다. 그 결과 작업이 순서대로 처리되어 갱신 손실이 막힌다.

[[sim:transaction-lock]]

#### Q. COMMIT과 ROLLBACK에 대해 설명해보세요.

> 핵심: COMMIT은 트랜잭션의 변경을 영구 확정하고, ROLLBACK은 변경을 모두 취소해 트랜잭션 시작 전 상태로 되돌린다.

- **COMMIT**: 커밋 전의 변경은 임시 상태이다. 커밋해야 비로소 다른 트랜잭션에도 보이며 영속된다.
- **ROLLBACK**: 오류가 나거나 로직상 취소가 필요하면 되돌린다.

이 두 명령 덕분에 원자성이 지켜진다. **SAVEPOINT**를 쓰면 트랜잭션 중간 지점까지만 부분적으로 되돌릴 수도 있다.

#### Q. 원자성(일관성, 고립성, 지속성)이 뭔가요?

> 핵심: 원자성은 트랜잭션을 쪼갤 수 없는 단위로 취급해서, 전부 반영되거나 전부 취소되게 하는 성질이다(all or nothing).

나머지 세 가지는 위 ACID 설명을 한 줄씩 말할 수 있으면 된다.

- 일관성: 끝난 뒤 규칙을 지키는 상태
- 고립성: 동시 실행 간섭 차단
- 지속성: 커밋 결과의 영구 보존

### Q. ⭐ DeadLock이란 무엇인지 설명해 주세요.

> 핵심: 데드락(교착 상태)은 둘 이상의 트랜잭션이 서로 상대가 쥔 lock을 기다리느라 영원히 진행하지 못하는 상태이다.
> 해결은 예방, 회피, 탐지 후 회복의 세 갈래이다.

**예시**

- T1은 계좌 X를 잠근 뒤 Y를 요청한다.
- T2는 Y를 잠근 뒤 X를 요청한다.

T1은 Y가 풀리길, T2는 X가 풀리길 기다리니 아무도 못 움직인다. 각자 가진 lock을 놓지 않은 채 **교차해서 기다리는 것**이 핵심 원인이다.

[[sim:deadlock]]

**해결 방법**

1. **예방**
   - 트랜잭션 시작 전에 필요한 lock을 한꺼번에 모두 확보한다.
   - 또는 모든 트랜잭션이 정해진 순서(예: 항상 테이블 번호가 낮은 쪽부터)로 lock을 잡게 해서 교차 대기를 구조적으로 없앤다.
   - 단점은 불필요한 데이터까지 잠그게 되어 동시 처리량이 떨어진다는 점이다.
2. **회피**
   - 자원을 요청할 때마다 시작 시각(timestamp) 같은 기준으로 기다려도 되는지 검사한다.
   - 데드락 위험이 있으면 일부 트랜잭션을 미리 중단시킨다(wait-die, wound-wait 방식).
3. **탐지와 회복**
   - 평소에는 제약 없이 실행하다가, 대기 관계(wait-for graph)에 사이클이 생기면 데드락으로 판단한다.
   - 희생자 트랜잭션 하나를 ROLLBACK해서 풀어 준다.
   - 대부분의 상용 DBMS가 이 방식을 쓴다.

실무에서는 **lock 순서를 통일**하고 트랜잭션을 짧게 유지하는 것이 가장 효과적인 예방책이다.

#### Q. deadlock을 해결하려면 어떻게 해야 하나요?

> 핵심: 예방(필요한 lock을 미리 확보하거나 순서 통일), 회피(timestamp로 위험한 요청 차단), 탐지와 회복(사이클 감지 후 희생자 롤백) 세 가지가 있다.

| 방식 | 특징 |
|---|---|
| 예방 | 데드락 조건을 원천 차단, 동시성 저하 |
| 회피 | 요청마다 검사하는 비용 |
| 탐지와 회복 | 평소 오버헤드 없음, 발생 후 롤백 비용 |

실제 DBMS는 대개 **탐지와 회복**을 기본으로 쓴다. 개발자는 lock 순서 통일로 발생 빈도를 줄인다.

## Index

### Q. Index가 왜 필요한가요?

> 핵심: 인덱스는 테이블의 검색 속도를 높이려고 만드는 별도의 정렬된 자료구조로, 대부분 B+tree를 쓴다.
> 책 뒤의 찾아보기처럼 전체를 훑지 않고 원하는 위치로 바로 이동하게 해 준다.

인덱스가 없으면 `WHERE` 조건에 맞는 행을 찾으려고 테이블의 모든 행을 처음부터 끝까지 비교해야 한다(**Full Table Scan**). 행이 수백만 개면 매우 느리다.

인덱스를 만들면 검색 대상 컬럼의 값을 정렬해 두었다가 거기서 빠르게 찾을 수 있다.

**구조**

인덱스는 B-tree, B+tree, Hash, Bitmap 등으로 구현할 수 있고 RDBMS에서는 **B+tree**가 기본이다.

특정 컬럼의 값(search-key)을 정렬하고, 각 값에 대응하는 실제 행의 위치(pointer)를 짝지어 별도 구조에 저장한다. 값과 위치만 들고 있어서 테이블 전체보다 훨씬 작다.

```sql
CREATE INDEX idx_member_name
  ON member(name);

SELECT * FROM member
  WHERE name = '이도현';
-- 인덱스에서 '이도현'을 먼저 찾고
-- pointer를 따라 해당 행으로 이동
```

**클러스터형 인덱스와 보조 인덱스**

- **클러스터형(clustered)** 인덱스
  - 테이블의 실제 행 자체가 키 순서로 정렬되어 저장된다. 사전의 본문이 가나다순인 것과 같다.
  - 보통 기본키에 자동으로 만들어지며(MySQL InnoDB 기준) 테이블당 하나뿐이다.
- **보조(secondary)** 인덱스
  - 행과 별도로 인덱스를 만들고 pointer로 행을 가리킨다.
  - `CREATE INDEX`나 UNIQUE 제약으로 만들며, 여러 개를 둘 수 있다.
  - InnoDB에서는 이 pointer가 기본키 값이라서, 보조 인덱스로 찾은 뒤 클러스터형 인덱스를 한 번 더 거친다.

[[sim:index-search]]

**장단점**

장점은 `SELECT ... WHERE`(그리고 JOIN, ORDER BY) 속도가 크게 빨라진다는 것이다.

단점은 두 가지이다.

1. **추가 저장 공간**: 인덱스 자체가 디스크와 메모리를 차지한다.
2. **쓰기 성능 저하**: INSERT, UPDATE, DELETE 때마다 인덱스도 정렬 상태를 유지하도록 같이 고쳐야 한다. B+tree 노드가 쪼개지거나 합쳐질 수도 있다.

#### Q. SELECT의 성능을 높일 수 있는 방법은 뭐가 있을까요?

> 핵심: 가장 대표적인 방법은 조건 컬럼에 인덱스를 거는 것이다.

인덱스가 있으면 전체 스캔 대신 정렬된 구조에서 해당 위치로 곧장 접근한다.

이 밖의 방법은 다음과 같다.

- 필요한 컬럼만 SELECT하기
- 조건절에서 컬럼에 함수나 연산을 씌우지 않기 (인덱스를 못 타게 됨)
- 실행 계획(**EXPLAIN**) 확인하기

#### Q. index의 내부 동작은 어떻게 되나요?

> 핵심: 대부분 B+tree로 구성되어 있어, 루트에서 내려가며 범위를 좁혀 조건에 맞는 데이터의 위치를 로그 시간에 찾는다.

루트와 중간 노드에서 어느 자식으로 내려갈지 정하고, 리프 노드에서 값과 pointer를 얻어 실제 행으로 간다.

자세한 구조는 아래 B+tree 질문에서 다룬다.

#### Q. index를 많이 생성하면 안되나요?

> 핵심: 안 된다. 인덱스가 늘수록 저장 공간과 쓰기 비용이 함께 늘기 때문에, 효과가 큰 컬럼에만 만들어야 한다.

행을 하나 넣거나 고칠 때마다 관련된 모든 인덱스를 같이 갱신해야 한다.

조회 이득이 쓰기 손실과 공간 비용보다 클 때만 만드는 것이 맞다.

### Q. ⭐⭐⭐⭐ index를 어느 column에 사용하는 것이 좋을까요?

> 핵심: WHERE나 JOIN에 자주 쓰이고, 값의 종류가 다양하며(카디널리티 높음), 조건으로 걸렀을 때 남는 행이 적고(선택도 낮음), 수정이 드문 컬럼이 좋다.

| 기준 | 적합한 방향 |
|---|---|
| 카디널리티 (고유 값의 개수) | 높을수록 적합 (중복이 적을수록 좋음) |
| 선택도 (조건으로 골랐을 때 남는 행의 비율) | 낮을수록 적합 |
| 조회 활용도 | WHERE, JOIN, ORDER BY에 자주 쓰일수록 적합 |
| 수정 빈도 | 낮을수록 적합 |

**용어 정의 주의**

카디널리티와 선택도는 정의가 자료마다 약간 다르다. 여기서는 이렇게 본다.

- 카디널리티: 고유한 값의 개수
- 선택도: 특정 값으로 조회했을 때 돌아오는 행의 평균 비율

카디널리티가 높을수록 선택도 수치는 낮아진다. 면접에서는 **정의를 먼저 밝히고** 말하면 안전하다.

**효과적으로 쓰는 기준**

- WHERE 절이나 JOIN 조건에 **자주 등장하는** 컬럼에 만든다.
- **수정이 잦은** 컬럼은 피한다. 값이 바뀔 때마다 인덱스의 정렬 위치도 다시 잡아야 한다.
- **중복이 많은** 컬럼은 효과가 작다.
  - 예를 들어 membership_level이 3종류뿐이면 값 하나로 조회해도 전체의 상당 부분이 나와서 전체 스캔과 별 차이가 없다.
  - 조회 결과가 전체의 소수(대략 몇 퍼센트 이내)일 때 이득이 크다.
- **데이터가 많을수록** 효과가 크다. 행이 몇십 개뿐이면 인덱스가 오히려 손해이다.
- 한 테이블에 인덱스를 **너무 많이** 만들지 않는다. 개수의 정해진 기준은 없지만 쓰기 비용이 쌓이므로 필요한 것만 둔다.
- 여러 컬럼을 같이 조회한다면 **복합 인덱스**를 고려한다. 컬럼 순서는 카디널리티가 높고 자주 쓰이는 것을 앞에 둔다.

#### Q. index를 쓰면 성능이 좋아지니까 모든 컬럼에 인덱스를 사용하면 성능이 더 좋겠네요?

> 핵심: 아니다. 인덱스는 조회에만 이득이고 쓰기와 공간에는 비용이어서, 모든 컬럼에 걸면 전체 성능이 오히려 떨어진다.

값을 수정하면 그 컬럼에 걸린 인덱스를 전부 갱신해야 하고, 인덱스마다 저장 공간도 먹는다.

또 **옵티마이저**는 쿼리당 보통 소수의 인덱스만 쓴다. 그래서 대부분의 인덱스는 쓰이지도 않으면서 비용만 낸다.

#### Q. 우리 회사의 고객 DB에서 성별 column에 index를 걸어주는게 좋을까요?

> 핵심: 걸지 않는 것이 좋다. 값 종류가 두세 개뿐이라 카디널리티가 매우 낮아 인덱스로 걸러지는 양이 거의 없기 때문이다.

특정 성별로 조회해도 전체의 절반 가까이가 나온다. 그래서 옵티마이저가 인덱스를 아예 무시하고 전체 스캔을 택하기도 한다.

그러면 공간과 쓰기 비용만 낭비하게 된다.

#### Q. true 또는 false 값을 갖는 column에서, true 1%, false 99%의 비율로 구성된 상황에서는 index를 거는게 좋을까요?

> 핵심: 일반적으로는 카디널리티가 낮아 비추천이지만, 거의 항상 소수 쪽(true 1%)만 조회한다면 걸 수 있다.

값의 종류가 둘뿐이라 카디널리티는 낮다. 그러나 분포가 심하게 치우쳐 있고 쿼리가 항상 1% 쪽만 찾는다면, 그 조회에서는 선택도가 낮아 인덱스가 실제로 이득이 된다.

이런 경우 해당 값에만 거는 **부분 인덱스**(PostgreSQL의 partial index 등)를 쓰기도 한다. 반대로 99% 쪽을 조회한다면 인덱스는 의미가 없다.

즉 카디널리티만이 아니라 **실제 쿼리 패턴과 데이터 분포**를 함께 보고 판단한다.

### Q. ⭐데이터를 검색을 할 때 hash table의 시간복잡도는 O(1)이고 b+tree는 O(logn)으로 더 느린데 왜 index는 hash table이 아니라 b+tree로 구현되나요?

> 핵심: 해시는 값 하나를 찾는 동치 검색만 빠르고 순서 정보가 없어서, 범위 검색과 정렬을 지원하지 못한다.
> B+tree는 항상 정렬된 상태이고 쓰기와 삭제도 O(log N)이라 DB 인덱스에 더 적합하다.

DB 쿼리는 `=`뿐 아니라 `>`, `<`, `BETWEEN`, `ORDER BY`, `LIKE 'abc%'` 같은 범위와 정렬 조건이 매우 많다.

**해시 인덱스의 한계**

해시 함수는 비슷한 입력도 전혀 다른 위치로 흩뿌리기 때문에, **키 순서가 보존되지 않는다**. 따라서 `age >= 30` 같은 조건에는 쓸 수 없고 전체를 뒤져야 한다.

동치 검색(`=`)만 잘 되는 특수한 용도에 한정된다.

**B+tree가 인덱스에 적합한 이유**

1. 키가 항상 **정렬**되어 있어 범위 검색과 정렬에 유리하다.
2. 검색, 삽입, 삭제 모두 균형을 유지하며 **O(log N)**이다.
3. 트리 높이가 매우 낮다.
   - 노드 하나가 디스크 페이지 한 장 크기이고, 한 노드에 키를 수백 개 담는다.
   - 그래서 높이가 보통 3~4층이고, 수억 건이어도 디스크 접근이 몇 번이면 끝난다.
4. 실제 데이터 위치(pointer)는 **리프 노드**에만 있고, 리프끼리 서로 연결되어 있다. 범위 검색은 시작 값을 찾은 뒤 리프를 옆으로 따라가기만 하면 된다.

구조를 정리하면, 루트와 중간 노드는 길 안내용 키만 가지고 있고 리프에 실제 (키, pointer) 쌍이 정렬되어 있다.

[[sim:bplus-tree]]
