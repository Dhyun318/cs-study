# 자료구조

## Array & Linked List

### Q. Array는 어떤 자료구조인가요?

> 핵심: 같은 타입의 원소를 메모리의 연속된 칸에 나란히 놓고, 크기를 만들 때 고정하는 자료구조다.
> 인덱스로 주소를 바로 계산하므로 조회가 O(1)이고, 중간 삽입/삭제와 크기 변경에는 약하다.

Array의 핵심은 **연속된 메모리**이다. 시작 주소를 알면 i번째 원소의 위치는 `시작 주소 + i × 원소 크기`로 곧바로 계산된다.

앞에서부터 세어 볼 필요가 없어서 몇 번째 원소든 한 번의 계산으로 읽는다. 이것이 **random access**이다.

**장점**

- 인덱스 조회 O(1)
- 끝에 추가 O(1)
- 원소들이 붙어 있어 순회할 때 CPU 캐시를 잘 탄다

**단점**

- 생성 시 크기를 정해야 한다
  - 크게 잡으면 빈 칸만큼 메모리를 낭비한다
  - 작게 잡으면 모자란다
- 중간에 끼워 넣거나 빼면 뒤쪽 원소를 한 칸씩 밀거나 당겨야 한다

| 연산 | 시간복잡도 |
|---|---|
| 인덱스 접근 | O(1) |
| 끝에 추가 / 끝 삭제 | O(1) |
| 중간 삽입 / 삭제 | O(n) |
| 값으로 검색(정렬 안 됨) | O(n) |

면접에서 Array는 거의 항상 Linked List와 **한 쌍**으로 묻는다. 메모리에 놓이는 방식이 다르고, 그 차이가 연산 비용 차이로 이어진다는 흐름으로 답하면 된다.

#### Q. 예상보다 많은 데이터가 들어와 Array 크기를 넘으면 어떻게 하나요?

1. 기존보다 큰 새 배열을 만든다.
2. 원소를 모두 복사한다.
3. 옛 배열을 해제한다.

이렇게 크기를 스스로 늘리는 배열이 **Dynamic Array**이다.

크기를 도무지 예측할 수 없다면 처음부터 **Linked List**를 써서 원소가 들어올 때마다 노드 하나씩 할당하는 방법도 있다.

### Q. Dynamic Array는 어떤 자료구조인가요?

> 핵심: 가득 차면 더 큰 배열을 새로 잡아 옮겨 담는 방식으로 크기 제한을 없앤 배열이다.
> 가끔 O(n) 복사가 일어나지만 길게 보면 append는 평균 O(1)(amortized)이다.

고정 크기 Array는 용량을 넘기면 더 담을 수 없다. Dynamic Array는 내부에 **용량(capacity)**을 따로 두고, 실제 원소 수(size)가 용량에 닿으면 더 큰 배열을 만들어 옮긴다.

이 작업이 **resize**이다. Python의 list, Java의 ArrayList, C++의 vector가 모두 이 구조이다.

[[sim:dynamic-array]]

**Doubling**

용량을 늘리는 대표 방식은 **두 배로 키우는 것**이다. 용량이 4인 배열에 5번째 원소를 넣으면 용량 8짜리를 새로 만들고 기존 4개를 복사한다.

이때 한 번은 O(n)이다. 늘리는 배율은 구현마다 다르다(Java ArrayList는 약 1.5배).

**분할상환 분석(amortized)**

append가 O(1)이라고 했다가 O(n)이라고도 하니 어느 쪽이냐는 질문이 자주 따라온다. 답은 **평균 O(1)**이다.

- 용량이 1에서 시작해 두 배씩 커진다고 하자.
- n개를 넣는 동안 복사는 1, 2, 4, ... 개씩 일어나고, 합은 2n보다 작다.
- 복사 총량이 O(n)이므로 append 하나당 평균 O(1)이다.
- 비싼 resize 비용을 값싼 append 여러 번이 나눠 낸다고 이해하면 된다.

주의할 점은 이것이 **평균**이라는 것이다. resize가 걸린 그 한 번의 append는 실제로 느리다.

#### Q. Dynamic Array를 Linked List와 비교해 장단점을 설명해 주세요.

**장점**

- 인덱스 접근이 O(1)이다. `시작 주소 + 인덱스 × 원소 크기`라는 계산 한 번이면 된다.
- 끝에 추가/삭제가 amortized O(1)이다.
- 원소가 연속해 있어 캐시 적중률이 높다.
- 포인터를 따로 저장하지 않아 원소당 메모리가 작다.

**단점**

- 끝이 아닌 곳에 삽입/삭제하면 뒤쪽 원소를 모두 밀어야 해서 O(n)이다.
- resize가 일어나는 순간 지연이 튄다. 응답 시간이 일정해야 하는 시스템에서는 문제가 될 수 있다.
- 늘릴 때 여유분을 넉넉히 잡으므로 쓰지 않는 빈 공간이 생긴다.

### Q. Linked List에 대해서 설명해 주세요.

> 핵심: 값과 다음 노드의 주소를 담은 노드를 포인터로 이어 붙인 자료구조다.
> 메모리에는 흩어져 있어도 next를 따라가면 순서가 이어지는 논리적 연속성을 갖는다.

```python
class Node:
    def __init__(self, value):
        self.value = value   # 저장할 값
        self.next = None     # 다음 노드를 가리키는 참조
```

노드는 필요할 때마다 따로 할당되므로 물리적 위치가 제각각이다. 대신 각 노드가 **다음 노드의 주소**를 들고 있어서, head에서 출발해 next를 따라가면 순서대로 모든 원소에 닿는다.

Array는 메모리 배치로 순서를 보장하고, Linked List는 **포인터**로 순서를 보장한다고 정리할 수 있다.

[[sim:linked-list]]

**시간복잡도**

| 연산 | 시간복잡도 | 비고 |
|---|---|---|
| 인덱스 접근 / 검색 | O(n) | head부터 순서대로 따라가야 함 |
| 삽입 / 삭제 | O(1) | 해당 위치의 노드를 이미 안다는 전제 |

- 삽입은 새 노드를 만들고 앞 노드의 next와 새 노드의 next, 이 두 개만 바꾸면 끝난다.
- 원소를 밀 필요가 없다.
- 삭제도 앞 노드의 next를 건너뛰게 바꾸면 된다.

**비용**

- 노드마다 포인터 하나를 더 저장하므로 원소당 메모리가 더 든다.
- 노드가 흩어져 있어 캐시 효율이 떨어진다.
- 양방향 순회가 필요하면 prev 포인터도 가진 **Doubly Linked List**를 쓴다.

Linked List는 Stack, Queue, 해시 테이블의 체이닝, 그래프의 인접 리스트처럼 다른 자료구조의 **부품**으로 자주 쓰인다.

### Q. ⭐ Array와 Linked List를 비교해서 설명해 주세요.

> 핵심: Array는 연속 메모리라 조회가 O(1)이고 삽입/삭제가 O(n)이다. Linked List는 포인터로 연결돼 있어 조회가 O(n)이고 삽입/삭제 자체는 O(1)이다.
> 데이터 양을 알고 조회가 많으면 Array, 양을 모르고 삽입/삭제가 잦으면 Linked List를 쓴다.

| | Array | Linked List |
|---|---|---|
| 메모리 배치 | 연속 | 비연속(포인터로 연결) |
| 조회 | O(1) | O(n) |
| 삽입/삭제 | O(n) | O(1) (위치를 안다면) |
| 크기 | 고정(Dynamic Array는 가변) | 실행 중 자유롭게 증감 |
| 원소당 메모리 | 값만 | 값 + 포인터 |

**조회**

Array는 주소를 계산해 바로 읽는다. Linked List는 head부터 next를 따라 n번째까지 걸어가야 한다.

**삽입/삭제**

- Array: 끝은 O(1)이지만 중간이면 뒤 원소를 밀어야 해서 O(n)이다.
- Linked List: 포인터만 바꾸면 되니 O(1)이다.

다만 원하는 위치를 찾는 과정이 O(n)이라서, 값이나 인덱스로 위치를 찾아야 하는 상황에서는 합쳐서 O(n)이다.

이미 **노드를 들고 있거나** head/tail에 넣고 빼는 경우에 O(1) 이점이 살아난다.

**메모리**

- Array: 쓰지 않는 칸까지 미리 잡아 두므로 낭비가 생길 수 있다.
- Linked List: 필요한 만큼만 할당하지만 노드마다 포인터 비용이 붙는다.

데이터 양을 정확히 안다면 오히려 Array가 메모리를 덜 쓴다.

#### Q. 어느 상황에 Linked List를 쓰는 게 Array보다 나을까요?

- 맨 앞이나 중간(노드를 이미 가진 경우)에서 삽입/삭제가 잦을 때
- 저장할 데이터 개수를 전혀 예측할 수 없을 때
- 인덱스 조회가 거의 필요 없을 때

#### Q. 어느 상황에 Array를 쓰는 게 Linked List보다 나을까요?

- 인덱스로 임의 조회를 자주 할 때
- 데이터 개수를 미리 알고 있을 때
- 처음부터 끝까지 반복문으로 순회하는 일이 많을 때(연속 메모리라 캐시에 유리)
- 메모리를 아끼는 게 중요할 때(포인터 저장 비용이 없음)

#### Q. Array와 Linked List의 메모리 할당은 언제 일어나며, 메모리의 어느 영역을 쓰나요?

C 같은 언어를 기준으로 하면 다음과 같다.

- 지역 변수로 선언하는 고정 크기 배열
  - 크기가 컴파일 시점에 정해지는 **정적 할당**이다.
  - **Stack** 영역에 잡힌다.
- Linked List 노드
  - 새 원소가 들어올 때마다 실행 중에 `malloc`이나 `new`로 할당하는 **동적 할당**이다.
  - **Heap** 영역에 놓인다.

참고로 Java나 Python처럼 배열 객체도 `new`로 만드는 언어에서는 배열 역시 Heap에 올라간다. 면접에서는 고정 크기는 컴파일 시점, 가변 크기는 런타임이라는 구분을 중심으로 말하면 된다.

## Queue & Stack

### Q. Queue는 무슨 자료구조인가요?

> 핵심: 먼저 넣은 것이 먼저 나오는 FIFO 자료구조다. 한쪽 끝에 넣고(enqueue) 반대쪽 끝에서 뺀다(dequeue).
> 두 연산 모두 O(1)이며, BFS, 작업 스케줄링, 버퍼 등에 쓰인다.

줄 서는 상황과 같다. 가장 오래 기다린 요소가 가장 먼저 처리된다.

- 넣는 쪽을 **rear**(tail)라고 부른다.
- 빼는 쪽을 **front**(head)라고 부른다.

[[sim:queue-stack]]

**구현 방식**

- **배열 기반**
  - 앞에서 빼면 앞쪽 칸이 비고, 앞으로 계속 밀려가므로 낭비가 생긴다.
  - 그래서 인덱스를 끝에서 처음으로 되돌리는 **원형 큐**(circular queue)를 쓴다.
  - 인덱스는 `(idx + 1) % capacity`로 순환시킨다.
  - front와 rear가 같을 때 빈 상태인지 가득 찬 상태인지 구분하려고 원소 개수를 따로 세거나 한 칸을 비워 둔다.
- **연결 리스트 기반**
  - head에서 빼고 tail에 붙이면 된다.
  - 크기 제한과 재할당 걱정이 없다.

**변형**

- Deque(double-ended queue): 양쪽 끝에서 모두 넣고 뺄 수 있다.
- Priority Queue: 들어온 순서가 아니라 우선순위가 높은 것이 먼저 나온다.

**활용**

- 프린터 대기열
- CPU 작업 스케줄링
- 캐시(FIFO 교체)
- BFS 탐색
- 이벤트/메시지 큐

#### Q. 배열 기반과 리스트 기반 Queue의 차이는 무엇인가요?

**배열 기반**

- 보통 원형 큐로 만들어 공간을 재사용한다.
- 용량이 차면 Dynamic Array처럼 키워야 하므로 enqueue는 amortized O(1)이 된다.
- 캐시 효율이 좋아 평소에는 빠르지만, resize가 걸린 순간은 느리다.

**리스트 기반**

- 보통 단방향 연결 리스트에 head와 tail을 둔다.
- enqueue는 tail 뒤에 붙이고, dequeue는 head를 떼어 내므로 둘 다 매번 O(1)이다.
- 최악의 경우 지연이 없다는 것이 장점이다.
- 노드를 할당할 때마다 비용이 들고 포인터 메모리가 추가된다.

정리하면 두 구현 모두 연산은 O(1)이다. 배열은 평균적으로 빠르고 가끔 크게 느리며, 리스트는 일정하지만 평균 상수 비용이 더 크다.

### Q. Stack은 어떤 자료구조인가요?

> 핵심: 가장 나중에 넣은 것이 가장 먼저 나오는 LIFO 자료구조다. 한쪽 끝(top)에서만 넣고(push) 뺀다(pop).
> 두 연산 모두 O(1)이고, 함수 호출 스택, 괄호 검사, DFS, 뒤로 가기 등에 쓰인다.

접시를 쌓는 모양을 떠올리면 된다. 맨 위 접시만 꺼낼 수 있다.

배열의 끝이나 연결 리스트의 head를 **top**으로 삼으면 push와 pop이 각각 O(1)로 구현된다.

[[sim:queue-stack]]

**활용**

- 함수 호출과 복귀를 관리하는 call stack(재귀의 기반)
- 수식 괄호 짝 검사, 후위 표기식 계산
- 브라우저 뒤로 가기, 에디터의 undo
- DFS(깊이 우선 탐색)

면접에서는 Stack만 따로 묻는 일은 드물다. Queue의 FIFO와 대비되는 **LIFO**라는 점과 활용 예 몇 가지를 말할 수 있으면 충분하다.

### Q. Stack 두 개를 이용하여 Queue를 구현해 보세요.

> 핵심: 입력용 stack(in)과 출력용 stack(out)을 둔다. enqueue는 in에 push하고, dequeue는 out이 비었을 때만 in의 원소를 전부 out으로 옮긴 뒤 pop한다.
> stack을 한 번 거치며 순서가 뒤집히므로 먼저 들어온 값이 out의 top에 온다.

예를 들어 A, B, C 순서로 enqueue하는 경우이다.

1. in에는 아래부터 A, B, C가 쌓인다.
2. dequeue 때 in에서 하나씩 pop해 out에 push한다.
3. out은 아래부터 C, B, A가 되고, top인 A가 먼저 나온다.

**순서가 한 번 뒤집힌** 것이다. out에 원소가 남아 있는 동안은 in에서 옮기지 않아야 순서가 깨지지 않는다.

```python
class QueueWithStacks:
    def __init__(self):
        self.in_st = []    # 새 원소를 받는 쪽
        self.out_st = []   # 꺼낼 원소를 내보내는 쪽

    def enqueue(self, x):
        self.in_st.append(x)

    def dequeue(self):
        # 꺼낼 곳이 비었을 때만 한꺼번에 뒤집어 옮긴다
        if not self.out_st:
            while self.in_st:
                self.out_st.append(self.in_st.pop())
        if not self.out_st:
            raise IndexError("queue is empty")
        return self.out_st.pop()
```

이런 문제는 정답을 외웠는지보다 **순서를 뒤집는다**는 발상을 어떻게 끌어내는지를 본다.

#### Q. 시간복잡도는 어떻게 되나요?

- enqueue는 push 한 번이라 O(1)이다.
- dequeue는 out이 비어 있고 in에 n개가 있으면 n번 pop과 n번 push를 하므로 최악 O(n)이다.
- out에 원소가 있으면 dequeue는 pop 한 번이라 O(1)이다.
- 하지만 각 원소는 in에서 out으로 딱 한 번만 옮겨지고 한 번만 나간다.
- 그래서 연산 m번의 총 비용이 O(m)이고, dequeue도 **amortized O(1)**이다.

### Q. Queue 두 개를 이용하여 Stack을 구현해 보세요.

> 핵심: push는 한 queue에 enqueue만 한다. pop은 마지막 하나만 남기고 나머지를 다른 queue로 옮긴 뒤, 남은 하나를 꺼낸다.
> push O(1), pop O(n)이다.

Queue는 앞에서만 나오므로, 가장 최근에 들어온 원소(맨 뒤)를 꺼내려면 그 앞의 원소를 모두 비켜 놓아야 한다. 비켜 둘 장소가 **두 번째 queue**이다.

역할을 바꿔 가며 쓰기 위해 pop이 끝나면 두 queue의 참조를 교환한다.

```python
from collections import deque

class StackWithQueues:
    def __init__(self):
        self.main = deque()
        self.spare = deque()

    def push(self, x):
        self.main.append(x)

    def pop(self):
        if not self.main:
            raise IndexError("stack is empty")
        # 마지막 하나만 남기고 spare로 옮긴다
        while len(self.main) > 1:
            self.spare.append(self.main.popleft())
        top = self.main.popleft()
        self.main, self.spare = self.spare, self.main
        return top
```

반대로 push 때 새 원소를 넣고 앞의 n-1개를 다시 뒤로 돌려서 가장 최근 값이 맨 앞에 오게 하면 **push O(n), pop O(1)**로 비용을 옮길 수도 있다.

어느 쪽을 택했는지와 이유를 말할 수 있으면 된다.

#### Q. 시간복잡도는 어떻게 되나요?

- push는 enqueue 한 번이므로 O(1)이다.
- pop은 원소 n개 중 n-1개를 옮겨야 하므로 O(n)이다.

Stack 두 개로 Queue를 만들 때와 달리, 여기서는 옮기는 작업을 여러 번에 걸쳐 나눠 상환해 줄 수 없다. 그래서 pop이 **매번 O(n)**이다.

### Q. ⭐ Queue와 Priority Queue를 비교하여 설명해 주세요.

> 핵심: 일반 Queue는 들어온 순서(FIFO)로 나오고, Priority Queue는 우선순위가 가장 높은 원소가 먼저 나온다.
> 보통 Heap으로 구현하며 push와 pop이 O(log n)이다. Queue는 둘 다 O(1)이다.

| | Queue | Priority Queue(Heap) |
|---|---|---|
| 나오는 기준 | 들어온 순서 | 우선순위 |
| 넣기 | O(1) | O(log n) |
| 빼기 | O(1) | O(log n) |
| 최댓값/최솟값 확인 | 해당 없음 | O(1) (root) |

Priority Queue를 구현하라는 요청은 **Heap**을 구현하라는 뜻이다. 정렬된 배열이나 리스트로 만들면 삽입이나 추출 중 하나가 O(n)이 되므로, 둘 다 O(log n)인 Heap이 표준 선택이다.

활용은 다익스트라 최단 경로, 작업 스케줄러, 상위 k개 뽑기 등이다.

**Heap의 조건**

Heap은 **완전 이진 트리**이면서 다음 성질을 만족한다.

완전 이진 트리는 마지막 레벨을 빼고 가득 차 있고, 마지막 레벨은 왼쪽부터 채워진 트리이다.

- Min Heap: 모든 노드의 값이 자식 값보다 작거나 같다. root가 최솟값이다.
- Max Heap: 모든 노드의 값이 자식 값보다 크거나 같다. root가 최댓값이다.

형제끼리는 크기 관계가 없다. 전체가 정렬된 것이 아니라 부모와 자식 사이의 관계만 보장된다.

[[sim:heap]]

**배열로 구현하는 이유**

완전 이진 트리는 빈 칸 없이 위에서 아래, 왼쪽에서 오른쪽으로 채워지므로 배열에 그대로 담을 수 있다.

- 포인터 없이 인덱스 계산만으로 부모/자식을 찾는다.
- 마지막 위치에 새 노드를 붙이는 일도 배열 끝에 추가하는 것으로 끝난다.

인덱스를 1부터 쓰면 다음과 같다.

- 왼쪽 자식 = 2i
- 오른쪽 자식 = 2i + 1
- 부모 = i // 2

0부터 쓰면 부모는 `(i-1)//2`, 자식은 `2i+1`, `2i+2`이다.

**push, O(log n)**

1. 배열 맨 끝(트리의 마지막 위치)에 새 값을 넣는다.
2. 부모와 비교해 Min Heap 기준으로 부모보다 작으면 자리를 바꾼다. 이를 위로 올리는 **sift-up**이라고 한다.
3. 부모 이상이거나 root에 닿으면 멈춘다.

Min Heap [5, 12, 9, 20, 15]에 3을 넣으면, 끝에 붙은 3이 부모 9와 바뀌고 다시 부모 5와 바뀌어 root가 된다.

**pop, O(log n)**

1. root(최솟값)를 꺼내 반환한다.
2. 배열의 마지막 원소를 root 자리로 옮긴다.
3. 두 자식 중 더 작은 쪽과 비교해, 그 자식이 더 작으면 자리를 바꾼다. 아래로 내리는 **sift-down**이다.
4. 두 자식보다 작거나 같거나 leaf에 닿으면 멈춘다.

트리의 높이가 log n이고 비교/교환은 한 레벨에 한 번이므로 push와 pop 모두 O(log n)이다. Max Heap은 부등호 방향만 반대이다.

## Hash table & BST(Binary Search Tree)

### Q. ⭐⭐BST는 어떤 자료구조인가요?

> 핵심: 모든 노드에서 왼쪽 서브트리의 값은 더 작고 오른쪽 서브트리의 값은 더 큰 이진 트리다.
> 검색, 삽입, 삭제가 평균(균형일 때) O(log n)이고, 한쪽으로 치우치면 최악 O(n)이다.

BST는 값을 넣을 때부터 **정렬된 구조**를 유지한다. 규칙은 두 가지이다.

1. 어떤 노드든 왼쪽 서브트리의 값은 그 노드보다 작고, 오른쪽 서브트리의 값은 그 노드보다 크다.
2. 이 규칙은 모든 서브트리에 재귀적으로 적용된다.

예를 들어 40, 20, 60, 10, 30, 50, 70 순서로 넣으면 40이 root이고, 20과 60이 자식, 그 아래 10, 30, 50, 70이 이어진다.

주의할 점은 규칙이 직계 자식만이 아니라 **서브트리 전체**에 적용된다는 것이다. 20의 오른쪽 자식 자리에 45를 넣으면 부모 20보다는 크지만 root 40의 왼쪽 서브트리에 있으므로 틀린 BST이다.

[[sim:bst-structure]]

**검색**

찾는 값을 root와 비교해 작으면 왼쪽, 크면 오른쪽으로 내려간다. 한 번 비교할 때마다 후보의 절반을 버리는 셈이라, 균형 잡힌 트리의 높이 **log n**만큼만 내려가면 된다.

예를 들어 위 트리에서 30을 찾으면 3번 비교한다.

1. 40: 작다, 왼쪽
2. 20: 크다, 오른쪽
3. 30: 찾음

삽입도 같은 경로로 내려가 비어 있는 자리에 붙이면 된다.

[[sim:bst-search]]

**삭제**

- 자식이 없는 노드: 그냥 제거한다.
- 자식이 하나: 그 자식을 자기 자리에 올린다.
- 자식이 둘: 오른쪽 서브트리의 최솟값(후계자, **successor**)의 값으로 교체하고, 그 후계자 노드를 지운다.

**기타**

**중위 순회**(왼쪽, 자신, 오른쪽)로 읽으면 값이 오름차순으로 나온다. 이 때문에 정렬된 순회나 범위 검색이 필요할 때 BST가 쓰인다.

BST는 면접에 자주 나오고 난도도 있는 편이니, 삽입 과정을 그림으로 그려 설명할 수 있게 연습해 두는 것이 좋다.

#### Q. 이진 트리(Binary Tree)는 어떤 자료구조인가요?

모든 노드의 자식이 최대 2개(왼쪽, 오른쪽)인 트리이다. 값의 크기 규칙은 없다.

BST는 여기에 크기 규칙을 더한 이진 트리이고, Heap도 다른 규칙을 더한 이진 트리이다.

#### Q. BST의 최악 시간복잡도는 O(n)인데, 언제 발생하나요?

**트리가 한쪽으로 치우쳤을 때**이다. 이미 정렬된 순서(10, 20, 30, 40)로 값을 넣으면 매번 이전 노드의 오른쪽에만 붙어서 사슬 모양이 된다.

이러면 구조가 사실상 Linked List이고, 검색에 높이만큼, 즉 n번의 비교가 필요하다. log n이라는 높이는 **균형이 잡혔을 때만** 성립하는 값이다.

[[sim:bst-search]]

#### Q. 해결 방법은 무엇인가요?

삽입/삭제 때 스스로 균형을 맞추는 **Self-Balancing BST**를 쓴다. 높이를 항상 O(log n)으로 보장한다.

- **AVL 트리**
  - 노드마다 좌우 서브트리 높이 차(balance factor)를 -1, 0, 1 이내로 유지한다.
  - 어긋나면 회전(rotation)으로 바로잡는다.
  - 균형이 엄격해 검색에 유리하다.
- **Red-Black 트리**
  - 노드에 색을 두는 규칙으로 가장 긴 경로가 가장 짧은 경로의 두 배를 넘지 않게 한다.
  - 회전이 적어 삽입/삭제에 유리하다.

Java의 HashMap은 한 bucket의 체인이 길어지면(기본 8개 이상, 테이블 크기 조건 포함) 연결 리스트를 Red-Black 트리로 바꿔 최악 검색을 O(log n)으로 낮춘다.

C++의 `std::map`, Java의 `TreeMap`도 Red-Black 트리 기반이다.

### Q. ⭐⭐ Hash table은 어떤 자료구조인가요?

> 핵심: key를 해시 함수에 넣어 나온 값으로 저장 위치를 정하는 key-value 자료구조다.
> 저장, 삭제, 검색이 평균 O(1)이다. 충돌이 심하면 O(n)까지 느려질 수 있고, 빈 칸을 미리 확보하므로 공간 효율은 낮다.

**Direct-address Table이 부족한 이유**

key 값 자체를 배열 인덱스로 쓰는 방식이다. 키가 1부터 100 사이의 작은 정수라면 딱 맞지만, 일반적으로는 다음 문제가 있다.

- 키 범위가 넓으면 낭비가 크다. 회원 번호가 1000001부터 시작하는데 회원이 50명뿐이라면 백만 칸짜리 배열의 대부분이 비어 있다.
- 키가 정수가 아니면 쓸 수 없다. `"alice"` 같은 문자열은 인덱스가 될 수 없다.

[[sim:hash-storage]]

**Hash table의 아이디어**

**해시 함수** h로 키를 작은 범위의 인덱스로 바꿔 저장한다. 칸이 7개이고 `h(k) = k mod 7`이라면 다음과 같다.

- 키 1032는 인덱스 3
- 키 2055는 인덱스 4
- 키 3100은 인덱스 6

문자열 키는 먼저 문자 코드를 조합해 정수로 만든 뒤 mod를 취한다. 이 칸 하나하나를 **bucket** 또는 slot이라고 한다. key는 중복될 수 없다.

**Collision**

서로 다른 키가 같은 인덱스로 가는 것이 **충돌**이다. 키 1039도 `1039 mod 7 = 3`이라 1032와 같은 칸이다.

키의 가짓수가 칸 수보다 많은 한 충돌은 피할 수 없으므로 다음과 같이 대응한다.

- 해시 함수를 고르게 설계해 충돌을 줄인다.
- 생긴 충돌은 체이닝이나 open addressing으로 처리한다.

[[sim:hash-collision]]

**시간/공간**

- 시간: 저장, 삭제, 검색 모두 평균 O(1)이다. 모든 키가 한 칸에 몰리는 최악에는 O(n)이다.
- 공간: 충돌을 줄이려고 여유 칸을 두므로 빈 칸이 많아진다. 채워진 비율(**load factor**)이 높아지면 테이블을 키우고 재배치(rehash)한다.

해시 테이블은 실무 활용도가 높고, 답하다 보면 Array, Linked List, Tree까지 꼬리 질문이 이어져서 **면접 단골**이다.

#### Q. 좋은 hash function의 조건은 무엇인가요?

- 계산이 빠르다.
- 결과가 전체 인덱스 범위에 고르게 퍼진다(충돌이 적다).
- 같은 키는 항상 같은 값을 낸다(결정적).

가장 중요한 것은 **균등한 분포**이다.

키가 특정 패턴(예: 끝자리가 늘 0)을 가질 때 `mod`로 나누는 수를 짝수나 10의 거듭제곱으로 하면 값이 한쪽에 몰리기 쉽다. 그래서 테이블 크기를 **소수**로 잡는 방법을 흔히 쓴다.

### Q. ⭐⭐⭐⭐ Hash table에서 collision이 발생하면 어떻게 되나요? 해결방법에는 무엇이 있나요?

> 핵심: 크게 두 가지다. Open addressing은 정해진 규칙으로 다른 빈 칸을 찾아 저장하고, Separate chaining은 한 칸에 연결 리스트를 달아 같은 칸에 모아 저장한다.
> 둘 다 평균 O(1)이지만 충돌이 몰리면 O(n)까지 느려진다.

**Open addressing**

충돌이 나면 테이블 안의 다른 빈 칸을 규칙에 따라 찾는다(**probing**).

- 장점: 별도 구조를 만들지 않으므로 메모리가 적게 들고 캐시에도 유리하다.
- 단점: 테이블이 가득 찰수록 급격히 느려진다.
- 단점: 삭제 시 칸을 그냥 비우면 이후 탐색이 끊긴다.

그래서 삭제된 자리에 삭제 표시(**tombstone**)를 남긴다.

i번째 시도(i = 0, 1, 2, ...)에서 보는 위치는 다음과 같다.

- **Linear Probing**: `(h(k) + i) mod m`
  - 바로 옆 칸부터 확인한다.
  - 구현이 쉽고 캐시에 좋지만 데이터가 한 구간에 뭉친다.
- **Quadratic Probing**: `(h(k) + i²) mod m`
  - 제곱 간격으로 건너뛴다.
  - 뭉침이 줄지만 같은 시작 해시끼리는 같은 경로를 밟는다.
- **Double Hashing**: `(h1(k) + i × h2(k)) mod m`
  - 두 번째 해시로 간격을 정한다.
  - 키마다 경로가 달라 뭉침이 가장 적다.

예를 들어 m = 7에서 1032가 인덱스 3에 있는데 1039도 3으로 가면, Linear Probing은 4번 칸이 비어 있는지 보고 비었으면 거기에 넣는다. 검색할 때도 같은 순서로 따라가며 찾는다.

연속으로 찬 구간이 점점 길어지는 현상이 **클러스터링**이고, 이 구간에 걸린 키는 탐색 횟수가 늘어난다.

**Separate chaining**

각 bucket이 연결 리스트(또는 트리)의 head 역할을 한다. 충돌하면 그 bucket의 리스트에 노드를 추가한다.

- 삽입: 리스트 앞이나 뒤에 붙이면 되어 O(1)이다(중복 키 확인이 필요하면 검색이 더해진다).
- 검색/삭제: bucket을 찾는 것은 O(1)이고, 리스트를 훑는 비용이 더해져 평균 O(1 + 체인 길이)이다.
- 최악: 모든 키가 한 bucket에 몰리면 길이 n의 리스트 하나가 되어 O(n)이다.
- 개선: 체인이 길어지면 리스트 대신 균형 BST를 쓰면 최악이 O(log n)이 된다(Java HashMap 방식).

체이닝은 테이블이 가득 차도 계속 동작하고 삭제가 쉽다는 장점이 있다. 대신 노드마다 포인터와 할당 비용이 든다.

[[sim:hash-collision]]

**비교**

| | Open addressing | Separate chaining |
|---|---|---|
| 충돌 시 | 테이블 안의 다른 칸 | 같은 칸의 리스트에 추가 |
| 추가 메모리 | 없음 | 노드/포인터 필요 |
| 삭제 | tombstone 필요 | 간단 |
| load factor 한계 | 1을 넘을 수 없음 | 1을 넘어도 동작 |

#### Q. 최악 O(n)이라고 했는데, 어떤 상황인가요?

n개의 키가 모두 **같은 해시값**을 가져서 한 bucket에 몰리는 경우이다. 체이닝에서는 길이 n의 리스트가 만들어지고, 특정 키를 찾으려면 그 리스트를 끝까지 훑어야 하므로 O(n)이다.

이런 상황은 다음 경우에 생길 수 있다.

- 해시 함수가 나쁜 경우
- 입력이 일부러 같은 해시값을 만들도록 조작된 경우

#### Q. 이중 해싱(Double Hashing)이 무엇인가요?

Open addressing에서 충돌 시 다음 칸을 고르는 방법의 하나이다.

Linear나 Quadratic Probing은 같은 칸에서 충돌한 키들이 똑같은 경로를 밟기 때문에 뭉침이 생긴다. 이중 해싱은 **해시 함수를 두 개** 쓴다.

- h1: 처음 위치를 정한다.
- h2: 충돌 시 건너뛸 간격을 정한다.

따라서 같은 칸에서 충돌한 키라도 h2가 다르면 서로 다른 경로로 빈 칸을 찾는다.

h2에는 조건이 있다.

- 결과가 0이 되면 안 된다.
- 테이블 크기와 서로소여야 모든 칸을 방문할 수 있다(보통 크기를 소수로 둔다).
