# 네트워크

## TCP/IP

### Q. OSI 7계층과 TCP/IP 4계층을 비교하여 설명해 주세요.

> 핵심: **OSI 7계층**은 통신 기능을 일곱 단계로 쪼갠 참조 모델이고, **TCP/IP 4계층**은 실제 인터넷이 쓰는 실용 모델이다.
> 데이터는 계층을 지날 때마다 헤더가 붙고(캡슐화), 수신 쪽에서 벗겨진다(역캡슐화).

**계층 대응**

| OSI 7계층 | TCP/IP 4계층 | 대표 프로토콜 |
|---|---|---|
| 응용, 표현, 세션 | 응용 | HTTP, SMTP, FTP, DNS |
| 전송 | 전송 | TCP, UDP |
| 네트워크 | 인터넷 | IP, ICMP |
| 데이터 링크, 물리 | 네트워크 인터페이스 | Ethernet, Wi-Fi |

**두 모델의 차이**

- OSI는 개념을 설명하기 위한 **이상적인 분류**이다.
- TCP/IP는 프로토콜이 먼저 만들어진 뒤 정리된 모델이라, 위 세 계층(응용, 표현, 세션)을 하나로 묶는다.

**계층의 관계**

- 각 계층은 아래 계층의 기능을 빌려 쓰고, 위 계층에 기능을 제공한다.
- 계층 간 의존은 한 방향이다. 예를 들어 HTTP는 TCP 위에서, TCP는 IP 위에서 동작한다.
- 위쪽 계층은 보통 **소프트웨어**(브라우저, OS 네트워크 스택)가 맡는다.
- 아래쪽 계층은 보통 **하드웨어**(NIC, 스위치, 케이블)가 맡는다.

[[sim:encapsulation]]

**캡슐화와 역캡슐화**

- **캡슐화**: 송신 측에서 데이터가 응용 계층부터 아래로 내려갈 때 일어난다.
  - 각 계층이 자기 프로토콜의 제어 정보를 헤더로 앞에 붙여 아래 계층에 넘긴다.
  - 최종적으로 물리 계층에서 비트 신호가 된다.
- **역캡슐화**: 수신 측이 반대 순서로 올라가며 일어난다.
  - 계층마다 자기 헤더를 읽고 떼어낸 뒤 위 계층에 넘긴다.
  - 마지막에는 원래 데이터만 남는다.

**데이터 단위 이름**

- 전송 계층: segment(TCP), datagram(UDP)
- 네트워크 계층: packet
- 데이터 링크 계층: frame

```
[HTTP 데이터]
[TCP 헤더][HTTP 데이터]
  <- segment
[IP 헤더][TCP 헤더][HTTP 데이터]
  <- packet
[Eth 헤더][IP 헤더][TCP 헤더]
[HTTP 데이터][Eth 트레일러]
  <- frame
```

**TCP/IP 5계층이라고도 하는 이유**

네트워크 인터페이스 계층을 데이터 링크와 물리로 나누면 **5계층**이 된다. 교재마다 4계층, 5계층을 섞어 쓰므로 어느 쪽 기준인지 먼저 밝히고 답하면 안전하다.

### Q. ⭐ TCP vs UDP를 비교해서 설명해 주세요.

> 핵심: **TCP**는 연결, 순서, 재전송, 속도 조절로 신뢰성을 보장하는 대신 헤더와 지연이 크다. **UDP**는 연결 없이 던지기만 하는 가벼운 프로토콜이라 빠르지만 유실과 순서 뒤바뀜을 책임지지 않는다.

**전송 계층의 역할**

IP가 호스트에서 호스트로 패킷을 옮긴다면, 전송 계층은 **포트 번호**로 호스트 안의 프로세스에서 프로세스로 데이터를 전달한다. 대표 프로토콜이 TCP와 UDP이다.

**선택 기준**

- 정확성이 중요하면 TCP
- 실시간성이 중요하면 UDP

**비교표**

| 항목 | TCP | UDP |
|---|---|---|
| 연결 | 연결형 (3-way handshake) | 비연결형 |
| 신뢰성 | 순서 보장, 재전송, 중복 제거 | 보장 안 함 |
| 제어 | 흐름 제어, 혼잡 제어, 오류 제어 | 없음 (checksum만) |
| 데이터 단위 | 바이트 스트림 (segment) | 메시지 경계 유지 (datagram) |
| 헤더 | 최소 20바이트 | 8바이트 |
| 속도 | 상대적으로 느림 | 빠름 |
| 용도 | 웹, 메일, 파일 전송 | 영상 통화, 게임, DNS |

**TCP가 신뢰성을 만드는 방법**

- **순서 번호**(Sequence number)와 **확인 응답**(ACK)으로 어디까지 받았는지 서로 확인한다.
- ACK가 제때 오지 않으면 타임아웃 후 재전송하고, 중복으로 온 segment는 버린다.
- checksum으로 훼손 여부를 검사한다.
- **흐름 제어**는 수신자의 버퍼가 넘치지 않도록 보내는 양을 조절한다(window size).
- **혼잡 제어**는 네트워크 자체가 막히지 않도록 전송량을 조절한다.

[[sim:tcp-udp-order]]

[[sim:tcp-udp-header]]

**헤더 비교**

- TCP 헤더: 순서 번호, 확인 번호, window size, 제어 플래그(SYN, ACK, FIN 등)
- UDP 헤더: 출발지와 목적지 포트, 길이, checksum 정도

이 헤더 크기 차이가 곧 **오버헤드** 차이이다.

**선택 기준 예시**

- 100MB짜리 설치 파일을 받는 경우: 한 바이트라도 깨지면 실행이 안 되므로 지연이 조금 늘어도 **TCP**가 맞다.
- 화상 회의: 0.3초 전의 프레임은 재전송으로 되살려도 이미 지나간 화면이라 소용없다. 일부 유실은 화면이 잠깐 깨지는 정도로 넘기고 최신 데이터를 계속 보내는 **UDP**가 낫다.
- 참고로 UDP 위에 필요한 신뢰성만 애플리케이션이 직접 얹는 방식도 있다(예: QUIC, HTTP/3).

### Q. 3-way handshake는 무엇이고 각 과정은 어떻게 되나요?

> 핵심: **3-way handshake**는 TCP 연결을 맺기 전에 양쪽이 통신 가능 상태이고 시작 순서 번호가 무엇인지 확인하는 세 번의 메시지 교환이다. SYN, SYN+ACK, ACK 순서로 진행되며, 끝나면 데이터를 주고받는다.

**목적**

TCP는 양방향 신뢰 전송을 하므로 데이터를 보내기 전에 서로 합의할 것이 두 가지 있다.

1. 상대가 살아 있고 받을 준비가 되었는지
2. 각자 사용할 **초기 순서 번호**(ISN)가 무엇인지

**과정**

1. 클라이언트가 **SYN**(자기 초기 순서 번호 포함)을 보낸다. 상태는 SYN_SENT이다.
2. 서버가 **SYN+ACK**를 보낸다. 클라이언트의 SYN을 확인하면서(ACK) 자기 초기 순서 번호도 알린다(SYN). 상태는 SYN_RECEIVED이다.
3. 클라이언트가 **ACK**를 보낸다. 양쪽이 ESTABLISHED가 되고 데이터 전송을 시작한다.

```
Client                 Server
  | --- SYN, seq=x ---> |
  | <-- SYN+ACK, seq=y, ack=x+1 -- |
  | --- ACK, ack=y+1 --> |
  |     (데이터 전송)     |
```

**두 번이 아니라 세 번인 이유**

- 서버도 자기 쪽 송신 순서 번호가 클라이언트에게 잘 전달되었는지 확인받아야 한다.
- 지연되어 뒤늦게 도착한 **옛 SYN** 때문에 서버가 헛되이 연결을 열어 두는 상황을 막는 효과도 있다.

[[sim:tcp-handshake]]

**TCP 통신의 세 단계**

1. 연결 설정: 3-way handshake
2. 데이터 전송
3. 연결 종료: 4-way handshake

HTTP/1.1과 HTTP/2는 TCP 위에서 동작한다. 그래서 웹 서버에 처음 접속할 때마다(연결을 새로 맺을 때) 이 과정이 일어난다.

#### Q. 그럼 4-way handshake는 뭔가요?

> 핵심: 연결을 닫는 과정이다. TCP는 양방향 통로를 각각 따로 닫기 때문에 FIN과 ACK가 두 쌍, 총 네 번 오간다.

1. 먼저 닫으려는 쪽(active close)이 **FIN**을 보낸다.
2. 상대가 **ACK**로 FIN을 받았다고 알린다. 이때 상대는 아직 보낼 데이터가 남았을 수 있어 연결은 반쯤만 닫힌 상태(half-close)이다.
3. 상대도 보낼 것을 다 보내고 나면(passive close) 자기 FIN을 보낸다.
4. 처음 닫은 쪽이 ACK를 보내고, 잠시 **TIME_WAIT**에서 기다렸다가 완전히 종료한다.

**TIME_WAIT를 두는 이유**

- 마지막 ACK가 유실되어도 상대의 FIN 재전송에 응답할 수 있도록 한다.
- 이전 연결의 늦은 패킷이 다음 연결에 섞이지 않게 한다.

**2번과 3번이 합쳐지지 않는 이유**

서버가 FIN을 받은 시점에 아직 전송할 데이터가 남아 있을 수 있기 때문이다.

## HTTP

### Q. HTTP가 뭔지 설명해 주세요.

> 핵심: **HTTP**(HyperText Transfer Protocol)는 클라이언트가 요청(request)을 보내면 서버가 응답(response)을 돌려주는 웹의 응용 계층 프로토콜이다. 연결을 유지하지 않고(Connectionless) 이전 요청을 기억하지 않는(Stateless) 것이 가장 큰 특징이며, 평문이라 암호화를 더한 것이 HTTPS이다.

**구조**

- 보통 TCP 위에서 동작한다(HTTP/3는 UDP 기반 QUIC).
- **요청 메시지**: 시작 줄(메서드, 경로, HTTP 버전), 헤더, (선택) 바디
- **응답 메시지**: 상태 줄(HTTP 버전, 상태 코드, 상태 문구), 헤더, (선택) 바디

```
GET /books?id=7 HTTP/1.1
  <- 시작 줄
Host: shop.example.com
  <- 헤더
Accept: application/json

HTTP/1.1 200 OK
  <- 상태 줄
Content-Type: application/json
  <- 헤더

{"id": 7, "title": "..."}
  <- 바디
```

[[sim:http-message]]

**특징**

- **Connectionless**: 요청과 응답을 한 번 주고받으면 연결을 끊는 모델이 기본 개념이다.
  - 서버가 연결을 오래 붙들고 있지 않아, 동시에 접속 자원을 점유하는 사용자가 줄어 더 많은 요청을 처리할 수 있다.
  - HTTP/1.1부터는 Keep-Alive로 연결을 재사용해 반복 handshake 비용을 줄인다.
- **Stateless**: 서버가 요청 사이의 상태를 저장하지 않는다.
  - 그래서 로그인 여부 같은 상태는 쿠키, 세션, JWT 같은 방법으로 요청마다 따로 실어 보내야 한다.
- **평문 전송**: 중간에서 가로채면 내용이 그대로 보이므로, TLS로 암호화한 HTTPS를 사용한다.

### Q. ⭐⭐ HTTP request method 중 GET vs POST를 비교 설명해 주세요.

> 핵심: **GET**은 리소스를 조회하는 메서드로 데이터를 URL의 쿼리 스트링에 실어 보내고, **POST**는 서버에 데이터 처리(주로 생성)를 요청하는 메서드로 데이터를 바디에 실어 보낸다. 이 차이 때문에 캐시, 히스토리, 데이터 길이 제한, 용도가 달라진다.

**비교**

| 항목 | GET | POST |
|---|---|---|
| 목적 | 조회 | 생성, 처리 요청 |
| 데이터 위치 | URL 쿼리 스트링 | 요청 바디 |
| 캐시 | 가능 | 일반적으로 안 함 |
| 브라우저 히스토리, 북마크 | URL이 그대로 남음 | 바디는 남지 않음 |
| 멱등성(같은 요청을 여러 번 해도 결과 동일) | 멱등, 안전 | 멱등 아님 |
| 길이 제한 | URL 길이 제한 있음 | 사실상 없음 |

```
GET /search?keyword=network&page=2 HTTP/1.1

POST /posts HTTP/1.1
Content-Type: application/json

{"title": "hello", "content": "..."}
```

**GET의 특징**

- 서버 상태를 바꾸지 않는 조회에 쓰므로 응답을 브라우저나 CDN이 재사용할 수 있다.
- 같은 URL을 공유하거나 북마크해도 같은 결과를 얻는다.

**POST의 특징**

- 같은 요청을 두 번 보내면 게시글이 두 개 생길 수 있어 **재시도**에 주의가 필요하다.

**보안 면의 주의**

- POST가 더 안전하다고 단정할 수는 없다. 둘 다 HTTPS가 아니면 평문이다.
- 다만 GET은 URL이 서버 로그, 히스토리, Referer 등에 남기 쉽다. 비밀번호 같은 **민감 값**을 쿼리에 넣으면 안 된다.

**그 밖의 메서드**

- PUT: 리소스 전체를 대체. 없으면 생성할 수 있음.
- PATCH: 리소스의 일부만 수정.
- DELETE: 리소스 삭제.

#### Q. HTTP request method 중 Put vs Patch를 비교 설명해 주세요.

> 핵심: 둘 다 기존 리소스를 수정하지만 **PUT**은 전체를 통째로 교체하고, **PATCH**는 보낸 필드만 부분 수정한다.

```
// 서버의 현재 상태
/members/5
{ "nickname": "kim",
  "city": "Busan", "age": 30 }

PUT /members/5
{ "nickname": "lee" }
// 결과: { "nickname": "lee" }
// <- 안 보낸 필드는 사라짐

PATCH /members/5
{ "nickname": "lee" }
// 결과: { "nickname": "lee",
//   "city": "Busan", "age": 30 }
// <- 나머지 유지
```

- PUT은 같은 요청을 반복해도 결과가 같은 **멱등** 메서드이다.
- PATCH는 설계에 따라 멱등이 아닐 수 있다(예: 값을 1 증가시키는 패치).
- PUT에는 전체 필드를 보내야 하므로, 일부만 바꿀 때는 PATCH가 편하다.

### Q. HTTP status code에 대해서 설명해 주세요.

> 핵심: **상태 코드**는 요청 결과를 알려 주는 세 자리 숫자로, 첫 자리에 따라 1xx부터 5xx까지 다섯 종류로 나뉜다. 클라이언트는 이 코드를 보고 성공 처리, 재시도, 로그인 유도 같은 후속 동작을 결정한다.

**분류**

- 1xx 정보: 요청을 받았고 처리를 계속하는 중
- 2xx 성공: 요청을 정상 처리함
- 3xx 리다이렉션: 다른 위치로 다시 요청해야 함
- 4xx 클라이언트 오류: 요청 자체에 문제가 있음
- 5xx 서버 오류: 요청은 유효했으나 서버가 처리에 실패함

**자주 쓰는 코드**

| 코드 | 이름 | 의미와 예시 |
|---|---|---|
| 200 | OK | 요청 성공 (상품 목록 조회) |
| 201 | Created | 새 리소스 생성 (회원가입, 글 등록) |
| 301, 302 | Moved, Found | 영구, 임시 이동 (http에서 https로 보내기) |
| 400 | Bad Request | 형식 오류로 이해할 수 없음 (필수 값 누락) |
| 401 | Unauthorized | 인증 안 됨 (로그인 없이 내 정보 요청) |
| 403 | Forbidden | 인증은 됐으나 권한 없음 (일반 회원이 관리자 페이지 접근) |
| 404 | Not Found | 대상 경로나 리소스가 없음 |
| 500 | Internal Server Error | 서버 내부 처리 오류 (예외 미처리) |
| 502 | Bad Gateway | 게이트웨이나 프록시가 상위 서버에서 잘못된 응답을 받음 |
| 503 | Service Unavailable | 과부하나 점검으로 일시적 응답 불가 |

**401과 403 구분**

- 401: 누구인지 모른다(**인증**).
- 403: 누구인지는 알지만 허용되지 않는다(**인가**).

### Q. ⭐⭐ www.google.com을 주소창에 쳤을 때 화면이 나오기까지의 과정을 네트워크 관점으로 설명해 주세요.

> 핵심: 도메인을 **DNS**로 IP 주소로 바꾸고, 그 IP로 TCP 연결을 맺어 HTTP 요청을 보내면, 서버가 응답을 돌려주고 브라우저가 이를 렌더링한다. 요청과 응답 모두 계층을 따라 캡슐화되어 패킷으로 오간다.

**순서**

1. 브라우저가 입력한 URL을 해석해 스킴(https), 호스트, 경로로 나눈다. 브라우저 캐시나 HSTS 목록 등을 먼저 확인할 수 있다.
2. 호스트 이름의 IP를 알아내기 위해 **DNS 조회**를 한다.
   - 브라우저 캐시, OS 캐시, hosts 파일, 그다음 리졸버(DNS 서버) 순으로 질의한다.
   - 필요하면 루트, TLD, 권한 네임서버 순으로 재귀 탐색한다.
3. 얻은 IP와 포트(HTTPS는 443)로 **TCP 3-way handshake**를 수행한다. HTTPS라면 이어서 TLS handshake로 암호화 채널을 만든다.
4. 브라우저가 **HTTP 요청** 메시지를 만들어 전송한다. 이 메시지는 TCP segment, IP packet, 이더넷 frame으로 캡슐화되어 공유기와 여러 라우터를 거쳐 서버로 간다.
5. 서버 쪽에서는 역캡슐화로 HTTP 요청을 복원하고, 웹 서버나 애플리케이션이 요청을 처리한다.
6. 처리 결과(HTML 등)로 HTTP 응답 메시지를 만들어 같은 방식으로 클라이언트에 돌려보낸다.
7. 브라우저가 HTML을 파싱하고, 이 안에 참조된 CSS, JS, 이미지를 추가로 요청해 받은 뒤 **렌더링**하여 화면에 보여 준다.

[[sim:google-request]]

**꼬리 질문 대비**

- DNS 응답에는 **TTL**이 있어 그동안 캐시된다.
- 로컬 네트워크 밖으로 나갈 때는 게이트웨이의 MAC 주소를 **ARP**로 알아낸 뒤 frame을 보낸다.
- 프런트엔드 관점으로 물으면 파싱, 렌더링 과정을 더 자세히 설명한다.
- 백엔드 관점으로 물으면 로드 밸런서와 WAS 처리 과정을 더 자세히 설명한다.

## Authorization

### Q. ⭐ 쿠키와 세션의 차이점을 설명해 주세요.

> 핵심: **쿠키**는 브라우저에 저장되는 작은 key-value 데이터이고, **세션**은 서버에 저장하고 브라우저에는 식별자(session ID)만 쿠키로 맡기는 방식이다. 쿠키는 서버 부담이 적지만 조작과 노출 위험이 있고, 세션은 더 안전하지만 서버 메모리와 확장성 부담이 생긴다.

**왜 필요한가**

HTTP는 Stateless라서 서버는 요청 사이의 관계를 모른다. 로그인 후 다른 페이지로 이동할 때마다 다시 로그인하지 않으려면 상태를 이어 주는 장치가 필요한데, 그것이 쿠키와 세션이다.

**쿠키**

1. 서버가 응답 헤더 `Set-Cookie`로 쿠키를 내려 준다.
2. 브라우저가 쿠키를 저장한다. 유효기간을 지정하면 브라우저를 닫아도 남는다.
3. 이후 같은 서버로 가는 모든 요청에 브라우저가 `Cookie` 헤더로 자동 첨부한다.

**세션**

1. 로그인에 성공하면 서버가 사용자 정보를 세션 저장소에 만들고 session ID를 발급한다.
2. session ID를 쿠키에 담아 클라이언트에 보낸다.
3. 이후 요청마다 ID가 오면 서버가 저장소에서 해당 사용자 정보를 꺼내 쓴다.

[[sim:cookie-session]]

**비교**

| 항목 | 쿠키 | 세션 |
|---|---|---|
| 저장 위치 | 클라이언트(브라우저) | 서버 (클라이언트에는 ID만) |
| 보안 | 사용자가 열람, 변조 가능 | 서버에 있어 상대적으로 안전 |
| 서버 부하 | 거의 없음 | 접속자가 늘수록 저장소 사용량 증가 |
| 수명 | 만료 시각까지 유지 가능 | 서버가 만료, 삭제를 직접 통제 |
| 용량 | 도메인당 개수와 크기 제한(항목당 약 4KB) | 서버 자원 한도 내 |

#### Q. 세션이 보안도 좋은데 쿠키를 사용하는 이유는 뭔가요?

> 핵심: 세션은 서버 메모리나 저장소를 쓰므로 사용자가 많아질수록 비용과 확장 부담이 커지고, 가벼운 정보는 쿠키에 두는 편이 효율적이기 때문이다.

- 쿠키는 서버가 저장하거나 조회할 필요가 없으므로 응답이 빠르고 서버가 가볍다.
- 보안에 영향이 없는 값(언어 설정, 테마 등)까지 세션에 둘 이유가 없다.
- 세션도 결국 session ID를 전달하기 위해 쿠키를 사용한다. 그래서 둘은 대체 관계가 아니라 **보완 관계**이다.

#### Q. 쿠키의 사용 예를 아는 대로 말씀해 주세요.

> 핵심: 서버에 부담을 주지 않고 브라우저 쪽에 기억시켜도 되는 정보에 쓴다.

1. 비로그인 상태의 장바구니나 최근 본 상품 목록
2. 자동 로그인, 아이디 기억하기
3. 팝업의 일정 기간 다시 보지 않기 체크
4. 언어, 다크 모드 같은 사용자 설정
5. 방문 분석이나 광고 식별(서드파티 쿠키)

### Q. 쿠키와 세션을 이용한 로그인 방식을 화이트보드에 설명해 주세요.

> 핵심: 로그인 성공 시 서버가 세션을 만들고 session ID를 쿠키로 내려 주면, 브라우저가 이후 모든 요청에 그 쿠키를 자동으로 붙이고 서버는 ID로 사용자를 알아낸다. 화이트보드에는 브라우저, 서버, 세션 저장소 세 칸을 그리고 화살표에 순서대로 번호를 매겨 설명하면 된다.

[[sim:cookie-session]]

**그림으로 그릴 구성**

```
 브라우저            서버
    |                  |
    | 1 로그인(ID, PW) -> |
    |                  | 2 회원 정보 확인
    |                  | 3 세션 생성 ---> 저장소
    |                  |   {sid: A1B2 -> user 42}
    | <- 4 Set-Cookie: sid=A1B2
    | 5 요청 + Cookie: sid=A1B2 ->
    |                  | 6 sid 조회 ---> 저장소
    |                  | <- 7 user 42 정보
    | <- 8 사용자 맞춤 응답
```

**단계 설명**

1. 사용자가 아이디와 비밀번호로 로그인을 요청한다.
2. 서버가 DB의 회원 정보와 대조해 **인증**(authentication)한다.
3. 성공하면 세션 저장소에 사용자 정보를 만들고 예측 불가능한 session ID를 발급한다.
4. 응답 헤더 `Set-Cookie`로 session ID를 브라우저에 전달한다.
5. 브라우저는 쿠키를 저장하고, 이후 요청마다 `Cookie` 헤더로 자동 전송한다.
6. 서버는 받은 ID로 세션 저장소에서 사용자를 찾아 권한을 확인하고(**인가**, authorization) 요청을 처리한다.
7. 처리 결과를 응답으로 돌려준다. 로그아웃 시에는 서버가 세션을 삭제한다.

**인증과 인가**

- 인증(authentication): 누구인지 확인하는 것
- 인가(authorization): 그 사용자에게 해당 요청을 할 권한이 있는지 확인하는 것

**한계와 대책**

- **세션 하이재킹**: session ID가 탈취되면 서버는 진짜 사용자와 구별하지 못한다.
  - HTTPS를 사용한다.
  - 쿠키에 `HttpOnly`, `Secure`, `SameSite` 속성을 설정한다.
  - 만료 시간을 짧게 하고, 로그인 시 ID를 재발급한다.
- **확장성**: 서버가 여러 대일 때 한 서버에만 세션이 있으면 다른 서버로 요청이 갔을 때 로그인이 풀린다.
  - 세션 저장소를 Redis 같은 공용 저장소로 분리한다.
  - 또는 상태를 클라이언트가 가진 토큰(JWT) 방식을 검토한다.
- 세션 저장소를 위한 **추가 자원**이 필요하다.
